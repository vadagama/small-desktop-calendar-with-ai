# Собрать релиз Small Desktop Calendar

Команда пользователя «собери релиз» (также «собрать/выпусти релиз») означает
полный цикл ниже. Это явное поручение собрать приложение, опубликовать GitHub
Release и обновить инструкцию на GitLab Pages; не запрашивай повторное
подтверждение этих уже порученных действий. Само добавление или обсуждение
этого навыка не запускает выпуск. «Перезапусти» и «пересобери приложение»
сами по себе не поручают публикацию релиза.

## 1. Зафиксировать состав

- Прочитай `AGENTS.md`, проверь рабочее дерево, актуальные ветки и PR.
  Собери актуальную согласованную версию, включая принятые изменения пользователя.
  Не выпускай старую ветку и не подмешивай чужую незавершённую работу.
- Зафиксируй точный commit, версию и уникальный tag. Сверь существующие релизы,
  чтобы повторный запуск не создавал дубликат и не перезаписывал опубликованный
  артефакт под тем же именем. Сохраняй существующие релизы и историю Changelog.
- Найди действующие команды в `package.json`, `scripts/` и CI. Примени
  `wails` и `shipping-and-launch`, а при изменении CI —
  `ci-cd-and-automation`. Учитывай данное пользователем разрешение на публикацию.

## 2. Собрать production-приложение и DMG

- Выполни проверки, production build, сборку нативных компонентов (включая
  Whisper), упаковку `.app` и установочного `.dmg` существующими скриптами.
  Проверь целевую архитектуру, подпись пакета и скрытый запуск Wails.
- Для дистрибуции используй настроенные Developer ID и нотариализацию Apple.
  Локальная ad-hoc подпись не равна подписанному и нотариализованному релизу.
  Если нужной конфигурации нет, подготовь доступные артефакты и явно укажи
  ограничение; не объявляй их production-релизом для пользователей без основания.
- В пакет не входят credentials, API-ключи, cookies, сессии, пользовательские
  vaults, память, тестовые профили, реальные данные встреч и аудиозаписи.
  Веса Whisper скачиваются пользователем отдельно.
- Проверь готовый пакет с новым изолированным `-user-data-dir`, без переиспользования
  личного профиля. Small — signed out; логин, пароль и LLM-ключи пустые;
  Mood — «Нейтральный»; «Ваши инструкции», «Предпочтения встреч»,
  «Сохранённый контекст», «Группы участников», «Форматы встреч» — пустые.
  Не удаляй существующие профили. Детальные правила — в `AGENTS.md`.
- Проверь запуск упакованного приложения, основные сценарии, установщик,
  отсутствие пользовательских данных, размер и SHA-256 артефактов.
  Сохрани связь version/tag/commit/имя DMG/hash.

Для Ordo используй упаковку Wails через
`npm run package:wails:mac -- --release --notes <файл>`. Сверь стабильную
версию `X.Y.Z`, Developer ID и нотариальный профиль. Упаковщик использует
`SMALL_SIGN_IDENTITY`, `SMALL_NOTARY_PROFILE`, `SMALL_WAILS_UPDATE_TEAM` и
`SMALL_WAILS_UPDATE_KEY_FILE`. Данные Apple из `APPLE_SIGNING_IDENTITY`,
`APPLE_NOTARY_PROFILE` и `APPLE_TEAM_ID` передай в соответствующие параметры
`SMALL_*`. Для всех выпусков канала используй один ключ Ed25519.

## 3. Опубликовать GitHub Release

- Используй фактический GitHub remote проекта. Подготовь release notes по
  пользовательским изменениям с предыдущего релиза: добавлено, изменено,
  исправлено, существенные ограничения. Не выдавай спецификации за функции.
- Опубликуй релиз с проверенными tag и commit; приложи актуальный DMG,
  контрольные суммы и прочие артефакты, предусмотренные проектом.
- Проверь публичную доступность релиза и скачивание DMG. Имя файла, размер и hash
  должны совпадать с проверенным локальным артефактом.

Для Ordo приложи к одному стабильному выпуску `vX.Y.Z` файлы
`Ordo-X.Y.Z-arm64.dmg`, `Small-Calendar-Wails-X.Y.Z-arm64.zip` и
`latest-wails-mac.json`. Отметь выпуск как Latest и проверь загрузку манифеста
без входа в GitHub по адресу `releases/latest/download/latest-wails-mac.json`.
Сверь версию, URL, размер и SHA-256 архива с манифестом. Обновлятор Ordo
проверяет точное имя ZIP и тег в его URL.

## 4. Обновить инструкцию и GitLab Pages

- Источник инструкции — `docs/install/`. Добавь запись Changelog с версией,
  датой и понятным описанием актуальных фичей релиза. Сохрани прошлые записи.
- Обнови все ссылки на релиз и DMG, включая кнопку установки/обновления,
  дату, отображаемую версию, имя файла и размер. Убери устаревшую оговорку
  о несовпадении локальной сборки и DMG, когда опубликован именно этот релиз.
- Актуализируй шаги настройки LLM/Voice и использования функций, если они
  изменились; иллюстрации делай на чистом профиле без личных данных.
- Публикуй инструкцию именно на **GitLab Pages**. Найди существующий GitLab
  проект, Pages URL и pipeline в конфигурации и подключённых инструментах.
  Не подменяй GitLab Pages GitHub Pages и не придумывай адрес проекта.
  Если назначение или доступ отсутствуют, подготовь содержимое и запроси
  только недостающие данные; не объявляй публикацию выполненной.
- Деплой только публичных файлов инструкции (`index.html`, CSS, разрешённые
  assets), без остальных документов репозитория, исходных профилей и секретов.
- Дождись результата pipeline/deployment. Открой публичный Pages URL,
  проверь новую запись Changelog, версию и прямую ссылку DMG после публикации;
  проверь локальные якоря, изображения и узкую ширину экрана.

## Готовность и повторный запуск

Релиз готов только когда доступны проверенный production DMG в GitHub Release
и опубликованная инструкция на GitLab Pages, ссылающаяся на этот же DMG.
При частичном успехе перечисли выполненное и конкретный блокер. Повторяй только
незавершённый шаг, не создавая повторный релиз и не затирая рабочую публикацию.
Не обходи требования подписи, проверки и доступа ради отметки о завершении.

В ответе дай версию/tag, commit, ссылку GitHub Release, прямую ссылку DMG и
GitLab Pages, краткие изменения и результаты проверок. Не сообщай об успешной
публикации по одному лишь локальному build или завершённой отправке pipeline.
