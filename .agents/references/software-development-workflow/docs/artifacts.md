# Каталог артефактов продукта

Структура ниже определяет места хранения, а не требование сразу создать все файлы. Минимум при подключении: README, правила агента, конфигурация процесса и краткий HLD. Каталог ADR появляется с первым решением. Для существующего продукта сначала составляется карта текущих документов; перенос выполняется отдельным изменением.

```text
README.md
AGENTS.md
CONSTRAINTS.md                    # измеримые ограничения качества
CHANGELOG.md
.workflow/config.yaml             # выбранные версии и профиль
spec/
  capability-map.md               # несколько независимых возможностей
  SPEC-<module>.md                # спецификация или отдельное изменение
tasks/
  plan.md                        # активный план; соглашение upstream
  todo.md                        # только при локальном учёте задач
  archive/<change>/               # завершённые планы и списки задач
docs/
  architecture/
    hld/README.md                # весь HLD: контекст, компоненты, развёртывание, NFR
    lld/<module>/README.md
    decisions/ADR-0001.md
    decisions/ADR-0002.md
  contracts/
    api/<boundary>.md
    events/<event>.md
    data/<domain>.md
  debt/DEBT-0001.md
  initiatives/INIT-0001.md
```

| Артефакт / шаблон | Обязательное содержание | Условие создания и обновления |
| --- | --- | --- |
| [README](../templates/product-readme.md) | Назначение, запуск, команды, архитектура, участие | Каждый продукт; изменение интерфейса запуска |
| [Ограничения](../templates/constraints.md) | Метрика, порог, команда, владелец исключения | До реализации; изменение требований качества |
| [HLD](../templates/hld.md) | Контекст, границы, компоненты, потоки, развёртывание, NFR, риски | При подключении; изменение системной архитектуры |
| [LLD](../templates/lld.md) | Ответственность модуля, интерфейсы, состояния, алгоритмы, транзакции, ошибки | Сложная логика или границы модуля; изменение внутреннего устройства |
| [ADR](../templates/adr.md) | Контекст, варианты, решение, последствия, подтверждение принятия | Значимый или дорогой в отмене выбор; пересмотр — новый ADR |
| [Карта возможностей](../templates/capability-map.md) | Стабильные module ID, ответственность, зависимости, порядок | Несколько независимо проверяемых возможностей |
| [SPEC](../templates/spec.md) | Цели, сценарии, критерии, команды, структура, стиль, тесты, границы, отложенное | Новая возможность или значимое изменение |
| [План](../templates/plan.md) | Этапы, зависимости, риски, проверки, индекс задач | Работа требует декомпозиции; актуализация текущего плана |
| [Задачи](../templates/tasks.md) | ID, описание, критерии приёмки, проверки, зависимости, затрагиваемые файлы | Исполняемая работа; локальный файл либо внешний трекер |
| [API](../templates/api.md) | Потребители, авторизация, ошибки, идемпотентность, совместимость | Изменение внешнего или межмодульного интерфейса |
| [События](../templates/events.md) | Производитель, потребители, доставка, порядок, retries, эволюция | Наличие событийного взаимодействия |
| [Данные](../templates/data.md) | Владение, инварианты, consistency, хранение, миграция, удаление | Долговечные данные и изменение их модели |
| [Долг](../templates/debt.md) | Доказательство проблемы, последствия, риск, варианты, проверка закрытия | Подтверждённый долг; гипотеза сначала проверяется |
| [Инициатива](../templates/initiative.md) | Цель, эффект, область, метрика успеха, SPEC/задачи | Несколько связанных изменений; небольшому долгу достаточно задачи |

HLD хранится целиком в `docs/architecture/hld/README.md`: контекст, компоненты, развёртывание и NFR — разделы одного файла. LLD создаётся по модулю, а не по каждому исходному файлу. Все ADR находятся в `docs/architecture/decisions/ADR-NNNN.md`; уровень решения задаётся полем `level`, без подкаталогов `hld/` и `lld/`.

Контракты в Markdown описывают смысл и ссылаются на машинный первоисточник: OpenAPI, Protobuf, GraphQL, миграции, схемы событий или иной формат платформы. Их нельзя вручную дублировать целиком. Требование Markdown + frontmatter относится к документации, а не к исходникам, SQL, схемам контрактов и конфигурации.

Пути `spec/` и `tasks/` сохранены ради совместимости upstream. Собственные пути допускаются только с явной картой путей и проверкой вызывающих их адаптеров; симлинки и дубли документов не являются обязательным механизмом совместимости.

## Что переиспользовано из upstream

В [spec-driven-development, Phase 0](https://github.com/addyosmani/agent-skills/blob/8c99fa36d90068c82d547f7c12a9d67a3e95f4ee/skills/spec-driven-development/SKILL.md#phase-0-scope-check) явно заданы `spec/capability-map.md` и `spec/SPEC-<module>.md`. Они нужны для нескольких независимо проверяемых возможностей; отдельной небольшой задаче карта не требуется. Изменение уже выпущенной возможности оформляется отдельной delta SPEC по тому же skill.

`spec/impact/` и `spec/verification/` не являются выходными путями этого skill и не входят в наш стандарт. Оценка влияния и результаты проверок записываются в разделах плана и задач. Отдельных файлов `operations/` и `security/` тоже нет: необходимые сведения об эксплуатации и безопасности включаются в HLD/LLD, критерии SPEC и проверки задач. Применимые upstream skills по этим темам сохраняются.

Все документы продукта, включая текст, таблицы и подписи схем, пишутся на русском. Названия технологий, код, API-идентификаторы, YAML-ключи и значения перечислений сохраняются в техническом написании.
