# Go Product Platform — краткие инженерные принципы

- Отдавайте предпочтение модульному монолиту на Go и группировке пакетов по функциональности; не выбирайте микросервисы по умолчанию.
- Используйте Protobuf + Buf + Connect для сетевых команд; WebSocket — только там, где обоснован двусторонний обмен в реальном времени.
- Сохраняйте независимость доменной логики от Wails, HTTP-транспорта, SQLite и PostgreSQL.
- Используйте нативные Go, Vite и локальный PostgreSQL в повседневном цикле разработки. Избегайте пересборки Docker на каждой итерации.
- Каждой независимой задаче с изменением файлов выделяйте отдельное рабочее дерево Git; изолируйте БД, порты, временные файлы и артефакты E2E.
- Во время разработки запускайте затронутые модульные и компонентные тесты, а также локальные фоновые браузерные E2E.
- Финальная проверка должна относиться к неизменяемому коммиту-кандидату; устаревшие результаты E2E не принимаются.
- Предпочитайте внутрипроцессные модули Go для управления доступом, аудита, задач River, машин состояний, флагов функций, аналитики, поиска и уведомлений.
- Добавляйте инфраструктурные сервисы только при измеренной потребности и обоснованных эксплуатационных затратах.
- Граница безопасности встроенных возможностей проекта — серверная авторизация; флаги и проверки интерфейса её не заменяют.
- Не допускайте непроверенные внешние скрипты, секреты рабочей среды и привилегированные учётные данные в рабочих деревьях агентов.
