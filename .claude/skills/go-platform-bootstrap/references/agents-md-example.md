# Заказы — инструкции для агентов

Эти инструкции применяются ко всем агентам, работающим в этом репозитории:
Codex (desktop, CLI и IDE-интеграции), Zed Agent, Claude Code, OpenCode и совместимым
средам. Единственный источник правил продукта — этот файл; CLAUDE.md содержит
ссылку на него и отличия Claude Code. Пути указаны от корня репозитория.

## Правила на каждый запрос

Перед ответом, планированием, исследованием, правками или запуском команд:

1. Если `using-agent-skills` включён в engineering.yaml, откройте и прочитайте
   `.agents/skills/using-agent-skills/SKILL.md`. Если не включён, переходите
   к шагу 2. Повторяйте это для каждого сообщения пользователя, включая
   уточнения, вопросы, ревью и мелкие правки. Не опирайтесь только на описания
   навыков или память прошлых ходов. Для регулярной работы используйте
   локальные файлы; не скачивайте и не обновляйте upstream при каждом запросе.
2. Перед изменением кода прочитайте `.agents/references/docs/workflow.md`,
   карту `.agents/references/docs/upstream.md` и проектные полномочия
   `docs/agent-policy.md` (если создан).
3. Выберите применимые процессы: первичный справочник — таблица
   «Маршрутизация задач» ниже; она покрывает каждый навык, установленный
   в engineering.yaml. Прочитайте каждый выбранный `SKILL.md` перед работой,
   которой он управляет. Предпочитайте проектную копию одноимённому
   глобальному навыку.
4. Кратко сообщите на русском, какие навыки вы применяете и почему. Для
   простого вопроса достаточно навигационного навыка; не навязывайте
   реализационный процесс информационному запросу.
5. Следуйте выбранному флоу разработки и его чек-листам. Если в ходе хода
   задача меняется, пересмотрите выбор навыков.
6. Если нужный навык отсутствует или не читается, сообщите точный путь и
   ограничение. Не утверждайте, что навык применён, и не подменяйте его
   инструкциями по памяти.

## Маршрутизация задач

навык из engineering.yaml; при добавлении навыка добавьте строку.
`using-agent-skills` маршрутизируется шагом 1 правил на каждый запрос.

## Модели и харнесы по ролям

Перед этапом читайте `ai.roles` и `ai.assignments` в engineering.yaml. Роли:
documentation, code, ui, code_review, design_review, requirements, architecture.
Выбирайте реальное назначение; смена YAML не меняет исполнителя текущей сессии.
Если он не соответствует назначению, используйте поддерживаемое переключение
или передайте задачу с SPEC/T-ID, контекстом, SHA/diff и критериями проверки.
Не заменяйте модель молча. Ревью выполняется в отдельном контексте, даже если
назначена та же модель. Способы запуска и ограничения — в MANUAL.md.
OpenCode читает этот файл и `.agents/skills/`; его нативные адаптеры — `.opencode/`.

## Целевой UI и эксперименты

Для общего UI-набора используйте Impeccable вместе с выбранным kit и профильными
инженерными навыками; добавьте их в таблицу маршрутизации по фактическому составу.
Для целевого UI читайте `docs/ui/DESIGN.md` и `docs/ui/<имя SPEC>/vision.md`,
`components.md`, `screens.md`; поддерживайте их вместе с реализацией. Задачи,
требования и evidence остаются в инженерной SPEC. Не создавайте второй backlog.
Прототипы в `prototypes/PROTOTYPE-NNNN-slug` проверяют отдельные гипотезы на общем стеке;
их README хранит результат. Переносите в целевой UI принятые решения; код — после
оценки пригодности. UI-навыки применяются независимо от наличия прототипов.

## Контекст продукта

- Цель: внутренний сервис управления заказами оптовой торговли — каталог,
  корзина, оформление, статусы и история заказов.
- Архитектура: Go-модуль `orders`; HTTP API на Connect по контрактам `proto/`;
  PostgreSQL через `pgx` и `sqlc`, миграции `goose`. Слои и границы — в
  `docs/hld/README.md`.
- UI: Vite + React + TypeScript в `web/`, компоненты shadcn, Tailwind v4;
  токены в `web/src/styles.css`.
- Данные: справочники контрагентов и номенклатуры синхронизируются из учётной
  системе; владение данными описано в `docs/hld/README.md`, схема — в миграциях.
- Ограничения: секреты только через окружение; прямые записи в
  production-БД запрещены.

## Конвенции работы

- Отвечайте на русском, если пользователь не попросил другой язык.
- Перед правками смотрите фактические файлы и `git status`; сохраняйте
  существующие изменения пользователя, включая untracked-файлы. Для поиска
  используйте `rg`.
- Изменения делайте маленькими и управляемыми; существенные допущения
  формулируйте явно. Спрашивайте, только когда нехватка информации блокирует
  решение или требуется разрешение.
- Явные инструкции пользователя важнее правил флоу. Навыки не авторизуют
  коммиты, push, деплой и запись в production.
- Новые ветки: `<тип>/<краткое-описание>`, например `feature/planogramma`,
  если пользователь не указал иное.
- Секреты (ключи провайдеров, пароли БД) не храните в файлах репозитория.
- Запускайте проверки, соответствующие изменению; сообщайте, что прошло,
  что проверить не удалось и какие остались ограничения. Не приписывайте
  непроведённые проверки.

## Команды проверки

- `go test ./...` — модульные и интеграционные тесты Go.
- `go build ./...` — сборка модуля.
- `buf lint` и `buf generate` — контракты; после генерации пересоберите
  зависимые пакеты.
- `sqlc generate` — регенерация слоя доступа к данным после правки SQL.
- `goose up` — миграции dev-БД (параметры подключения в `MANUAL.md`).
- `pnpm typecheck` и `pnpm build` в `web/` — типы и production-сборка UI.
- `pnpm test:e2e` в `web/` — Playwright smoke; детали в `web/e2e/README.md`.

## Graphify — навигация по кодовой базе

- Навык: `.agents/skills/graphify/SKILL.md`. Для архитектуры, связей символов
  и влияния изменений сначала спрашивайте граф:
  `graphify query "<вопрос с именами символов или путей>"`. Если доступны
  MCP-инструменты Graphify (`query_graph`, `get_node`, `get_neighbors`,
  `shortest_path`, `graph_stats`), используйте их.
- Запросы делайте узкими (обычно 2000 токенов); не читайте весь JSON графа.
  Рёбра INFERRED — навигационные подсказки: перед правками проверяйте
  исходники.
- Перед анализом проверьте наличие и актуальность графа: manifest, изменённые,
  новые и удалённые файлы области анализа, pending-маркеры. Чистый git status
  и один `graphify check-update .` не доказывают актуальность графа.
- Если графа нет, соберите его по инструкции навыка с проектной `.graphifyignore`.
  Устаревший код обновите через `graphify update .`, документацию и изображения —
  через семантический цикл `/graphify . --update` в ADE. После правок обновите
  граф, прежде чем полагаться на него или завершать задачу.
- Git-хуки и `graphify watch .` автоматизируют обновление кода; pending для
  документов требует отдельного семантического обновления. Восстановление и
  конкретные команды продукта описаны в MANUAL.md. При установке через
  `graphify agents install` (либо `graphify codex install` по версии CLI)
  объедините эти правила с обслуживаемым разделом без дублирования, сохраняя
  маркеры Graphify, блок GPP и пользовательские инструкции.
- Если граф устарел, запрос не нашёл нужного или Graphify недоступен,
  используйте точечный `rg` и чтение исходников; сообщите об ограничении.
- `graphify-out/` генерируется локально и игнорируется Git; не коммитьте его.

## Правила агентной работы
- Ведите AGENTS.md и CLAUDE.md полностью на русском языке: заголовки, пояснения, правила и новые разделы. Сохраняйте без перевода только команды, пути, имена файлов, названия продуктов и технические идентификаторы. При настройке существующего продукта переведите и остальные разделы этих файлов, сохраняя смысл и силу всех пользовательских правил.
- Обязательно соблюдайте процесс разработки. Перед изменением прочитайте `.agents/references/docs/workflow.md`, карту `.agents/references/docs/upstream.md` и проектные полномочия `docs/agent-policy.md` (если создан); для Claude Code те же референсы лежат в `.claude/references/`.
- Используйте проектные навыки из `.agents/skills/` (Codex и OpenCode) и `.claude/skills/` (Claude), роли из `agents/` и материалы из `references/` этих каталогов. Эти версии имеют приоритет над одноимёнными глобальными навыками. Применяйте навыки по характеру задачи; не отменяйте обязательные проверки процесса.
- Держите разделы продукта в AGENTS.md, помимо блока платформы: правила на каждый запрос (перед сообщением выбирать применимые навыки из установленных проектных и сообщать на русском, какие применяются и почему; при наличии using-agent-skills начинать с его чтения), таблица маршрутизации задач по навыкам — она покрывает каждый навык из engineering.yaml, при добавлении навыка строка добавляется; краткий контекст продукта, конвенции работы, команды проверки и раздел навигации Graphify. CLAUDE.md — тонкая ссылка на AGENTS.md с отличиями Claude Code; правила продукта в нём не дублируются.
- Выбирайте исполнителей по ai.roles и ai.assignments в engineering.yaml; модель и харнес текущей сессии должны соответствовать назначению либо требуется явная передача работы. Ревью выполняйте в отдельном контексте. Способы запуска и ограничения храните в MANUAL.md.
- Для целевого UI поддерживайте docs/ui/DESIGN.md и vision.md, components.md, screens.md в docs/ui/<имя инженерной SPEC>/. UI-навыки применяются и к продукту, и к экспериментам prototypes/PROTOTYPE-NNNN-slug; прототип проверяет гипотезу, перенос решений в продукт проходит инженерную SPEC.
- Порядок работы: контекст → уточнение требований → проектирование → планирование → реализация → проверка → независимое ревью → выпуск → развитие. Выполняйте применимые согласования и проверки процесса разработки.
- Храните требования, HLD/ADR и технические решения SPEC, контракты и доказательства проверок в Git продукта; обновляйте затронутую документацию вместе с кодом. Не выдумывайте результаты или согласования.
- Настройка и запуск описаны в `MANUAL.md`. Состав и происхождение проектного набора зафиксированы в `engineering.yaml`; паспорт продукта — в `product.yaml`.
- Для управления набором читайте проектную копию `.agents/skills/go-project-platform-manager/SKILL.md` (для Claude Code — `.claude/skills/go-project-platform-manager/SKILL.md`). Перед установкой или обновлением покажите структурированный список навыков, источников, версий, агентов и референсов для согласования. Глобальное обновление не обновляет проектные копии.
- Если проектные материалы отсутствуют, завершите согласованную установку; не подменяйте их молча глобальными версиями. В новом worktree материалы приходят из Git; восстанавливайте только генерируемые артефакты (например, граф graphify).
