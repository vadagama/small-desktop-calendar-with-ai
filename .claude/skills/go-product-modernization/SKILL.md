# Модернизация существующего продукта

Результат — проверенная картина исходного продукта и выполненный разрешённый
объём преобразования. Исходный стек может быть любым: название платформы не
разрешает автоматически заменить его на Go. Различать рефакторинг с сохранением
поведения и миграцию стека; редизайн и новые функции — отдельные изменения.

## Вход и выбор объёма

Прочитать инструкции репозитория, engineering.yaml, MANUAL и существующую
документацию. Учитывать уже данные ответы. Если есть активная модернизация,
продолжить её по [контракту профиля](references/profile.md), не начинать аудит заново.

Для голого вызова уточнить только неизвестное, используя нативные варианты ADE
или чат: источник (текущий репозиторий / путь / Git URL), цель (рефакторинг /
миграция), объём (аудит / подготовка плана / реализация выбранных этапов), целевой
стек и ограничения. Если цель пока не определена, начать с аудита и вариантов,
не назначать стек самостоятельно. Не просить токены в чате.

- **Аудит:** осмотр, разрешённые проверки и отчёт; не менять реализацию, не
  устанавливать платформу и не переписывать профиль. При «только посмотреть»
  отчёт в чате; файл assessment — если запрошено сохранение результата.
- **План:** обследование, целевые решения, инициатива и подготовленная SPEC первого
  этапа. Не генерировать пустые SPEC всех будущих этапов и не менять код продукта.
- **Реализация:** выполнить согласованные этапы с проверками и ревью. Сам вызов
  навыка не разрешает production-переключение, удаление данных или публикацию.
  Уже разрешённые действия повторно не согласовывать; при нехватке разрешения
  сначала подготовить конкретный diff/план и проверки, затем спросить о действии.

## 1. Получить и обследовать продукт

Для удалённого источника клонировать в новый каталог, зафиксировать исходные ref
и SHA. Для локального — проверить Git status, ветку, worktree и незакоммиченные
изменения; не делать reset/clean и не менять checkout с потерей правок. Рабочий
каталог по умолчанию тот же репозиторий, в отдельной ветке/worktree при необходимости.
Отдельный целевой репозиторий использовать только по выбору пользователя, записав
источник и назначение; не переносить .git поверх другого репозитория.

Прочитать [аудит и артефакты](references/assessment.md). Сначала inspect build,
install и migration scripts, затем запускать применимые проверки в изолированном
dev/test-окружении с тестовыми данными. Не использовать production credentials.
Обнаружить стек, точки входа, интеграции, данные, авторизацию, CI/CD и текущее UI.
Установку зависимостей включать в разрешённый объём; чтение кода само по себе
не требует запуска всего bootstrap. Если запуск невозможен, продолжать статический
анализ, указав точную границу доказанного. Не называть непроверенный baseline рабочим.

Graphify использовать по установленному навыку, если он доступен и актуален;
иначе выполнять точечный поиск. Полная установка платформы/Graphify — отдельная
часть настройки, не обязательное условие аудита чужого репозитория.

## 2. Зафиксировать поведение и целевое решение

Отделить наблюдаемое поведение, подтверждённые требования, известные дефекты и
неизвестное. Для сохраняемых сценариев зафиксировать вход, выход, побочные эффекты
и доказательство. Добавлять characterization/контрактные тесты в режиме реализации;
при аудите только предлагать их. Не превращать случайную ошибку старого кода
в обязательную совместимость без решения.

Согласовать границы: что сохраняется, что меняется, какие потребители/API и данные
затронуты, допустимый простой, метрики производительности, условия приёмки и отката.
Сохранять существующий UI, если редизайн не запрошен. Целевой стек проверять по
документации выбранных версий. Для разных стеков рассмотреть постепенную замену
модулей/адаптеров; полный перенос выбирать с обоснованием, не по умолчанию.

До реализации подготовить конкретный первый срез и общий порядок этапов по
[контракту артефактов](references/assessment.md). Не заявлять весь продукт новым
стеком после переноса одного компонента.

## 3. Подготовить исполнителей и окружение

Если продукт ещё не настроен, передать bootstrap только согласованную настройку
инструментов, навыков и профиля, сохраняя исходное приложение; не запускать генератор
нового продукта поверх него. Для существующего набора использовать manager.
Список навыков определяется исходным и целевым стеками. Прочитать реально
установленные SKILL.md; отсутствующие источники проверить до установки.

| Работа | Навыки при наличии и применимости |
|---|---|
| Требования и границы | interview-me, spec-driven-development |
| Архитектура и контракты | api-and-interface-design, documentation-and-adrs |
| Переход | deprecation-and-migration, incremental-implementation, planning-and-task-breakdown |
| Проверки и отладка | test-driven-development, debugging-and-error-recovery |
| Ревью | code-review-and-quality; security-and-hardening для затронутых границ безопасности |
| Реализация | Навыки обоих стеков; UI-набор при изменении интерфейса |

Модели брать из ai.roles по [общему контракту](../../references/go-product-platform/platform/references/model-harness-configuration.md),
ADE — по [инструкции](../../references/go-product-platform/platform/references/ade-installation.md). Отдельная матрица
моделей модернизации не нужна. Не приписывать работу назначенной модели без
реального запуска. Reviewer работает в отдельном контексте.

## 4. Выполнить этап и проверить замену

Прочитать [реализацию, переключение и завершение](references/transition.md).
Работать по одной SPEC с единым tasks.md: сначала baseline сохраняемого поведения,
затем изменение и сравнительные проверки. Тесты нового стека дополняют, а не
заменяют контрактные проверки старых потребителей. Не маскировать расхождения
изменением ожидаемых результатов без принятого изменения требований.

Если проверки, доступы или критичное решение блокируют этап, зафиксировать причину,
сохранить рабочее состояние и продолжить независимые разрешённые задачи. Не удалять
старый путь ради прохождения нового. Отчёт должен различать завершённый этап,
частичный переход и завершённую модернизацию продукта.

## 5. Закрыть переход и вернуться к обычной разработке

Проверить критерии завершения из transition.md: основной стек/запуск/CI, реальные
данные и интеграции, эксплуатация, откат, старые зависимости. Обновить профиль по
[правилам состояния](references/profile.md), HLD и MANUAL по факту; сохранить
инициативу, ADR и evidence. После закрытия новые функции идут через обычный SDD.

Финальный отчёт: исходная ревизия и рабочая копия, выполненный объём, изменённые
артефакты/код, команды и результаты, ограничения, состояние этапа и всего перехода,
следующий исполнимый шаг. Не выдавать подготовленный план за выполненную миграцию.
