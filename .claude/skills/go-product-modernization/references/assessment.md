# Обследование и документы модернизации

## Обследование

В отчёте отделять факты (путь/команда/результат), выводы и неизвестное.

| Область | Что установить |
|---|---|
| Источник | Repository URL без credentials либо путь, ref, SHA, локальный diff и границы анализа |
| Продукт | Пользователи, критичные сценарии, подтверждённые требования, фактическое UI |
| Стек | Runtime/SDK, lockfiles, версии, приложения и пакеты, поддерживаемые ОС |
| Архитектура | Модули, точки входа, границы доверия, внешние зависимости |
| Контракты | API/события, потребители, авторизация, совместимость и ошибки |
| Данные | Схемы/миграции, объём и ограничения переноса, хранение и восстановление |
| Проверки | Запуск, build/test, сценарии, реальные результаты и отсутствующее покрытие |
| Эксплуатация | CI/CD, окружения, observability, способ выпуска и отката |
| Преобразование | Проблемы с доказательствами, варианты, зависимости, стоимость/риски качественно |

Не сохранять секреты, production-выгрузки и персональные данные в отчёт. Нельзя
сделать вывод «тестов нет» только по отсутствию одного привычного каталога.
Запросить недостающие знания о бизнес-поведении; предположения явно помечать.
Если baseline не запускается, описать восстановление как первый этап, не
сравнивать новую реализацию с вымышленным успешным запуском старой.

## Артефакты по объёму запроса

Следовать [контракту документов](../../../references/go-product-platform/platform/handbook/20-artifact-contract.md).
Пути ниже — внутри продукта; не создавать docs/data, interfaces, lld или
requirements. Номера продолжают последовательности продукта, существующие
документы дополняются без потери истории. ID уникальны, frontmatter использует
kind/status по контракту. Отчёт обследования: kind review, status draft до проверки;
инициатива: kind initiative; операционная инструкция: kind operation.

| Артефакт | Когда и содержание |
|---|---|
| `docs/hld/modernization-assessment.md` | Сохранённый аудит: таблица выше, baseline, неизвестное, варианты, рекомендации |
| `docs/hld/README.md` | Проверенное текущее устройство; целевые идеи не выдавать за существующую архитектуру |
| `docs/adrs/ADR-XXXX-<decision>.md` | Существенный выбор стека/стратегии, варианты, последствия; proposed до принятия |
| `docs/initiatives/INIT-XXXX-modernization.md` | Цель, scope, этапы, зависимости, критерии завершения, ссылки на SPEC и baseline |
| `docs/specs/SPEC-XXXX-<stage>/` | Шесть документов только начатого этапа: requirements, design, plan, tasks, verification, review |
| `docs/operations/modernization-cutover.md` | Когда нужно переключение/перенос данных: подготовка, порядок, критерии остановки и откат |
| `docs/ui/<SPEC>/` | Если меняется целевой UI; DESIGN.md обновляется для принятых общих решений |
| `MANUAL.md` | Проверенные команды старой/новой реализации, окружение, тесты и ограничения |
| `docs/README.md` | Карта актуальных SPEC, обследования и инициативы |

Для повторной инициативы не перезаписывать прошлый assessment/cutover: выбрать
имя с ID инициативы. Инициатива связывает этапы, но не дублирует задачи tasks.md.
Не создавать ADR без архитектурного решения и cutover без переключения.
Аудит без сохранения не создаёт документов; план не меняет реализацию.
Прототип для гипотезы опционален: `prototypes/PROTOTYPE-NNNN-slug/`, а не
новый каталог для целевой реализации.

## Сохраняемое поведение и план

В requirements.md этапа составить матрицу:

| Сценарий/контракт | Источник требования | Baseline (SHA, команда, результат) | Ожидание после перехода | Проверка |
|---|---|---|---|---|

Зафиксировать отдельно разрешённые изменения и дефекты, которые не сохраняются.
Сравнения учитывать недетерминизм (время, ID, порядок) явными правилами, не
широким удалением значимых полей. Указать применимые пороги производительности
и целостности данных; не придумывать универсальные числа.

Каждый этап инициативы содержит границу замены, зависимости, SPEC при её наличии,
критерий готовности, способ обратного переключения и временные адаптеры. Большой
переход планировать последовательностью исполнимых срезов. Независимые задачи
можно разделять по рабочим деревьям, не допуская конкурирующих миграций БД.
