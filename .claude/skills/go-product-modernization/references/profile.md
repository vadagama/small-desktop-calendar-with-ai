# Профиль и возобновление

`modernization` — необязательное расширение engineering schema 1.2. Отсутствие
или null означает, что процесс не заведён. Product schema не меняется. Блок
заполняется при подготовке плана/реализации; аудит только для чтения его не создаёт.
Существующие ai/ui/skills и неизвестные пользовательские поля сохраняются.

```yaml
modernization:
  kind: "stack-migration" # refactor | stack-migration
  status: "planned" # assessed | planned | in_progress | validating | blocked | paused | completed
  source:
    repository: "<URL без credentials либо локальный путь>"
    ref: "<исходная ветка или tag>"
    commit: "<полный исходный SHA>"
    local_changes: null # путь к сохранённому patch/описанию, если исходник был грязным
  target_repository: null # null = тот же репозиторий; иначе выбранный URL/путь
  source_stack: ["<подтверждённый исходный стек>"]
  target_stack: ["<согласованный целевой стек>"]
  scope: "<компоненты и сохраняемое поведение; явные исключения>"
  assessment: "docs/hld/modernization-assessment.md"
  initiative: "docs/initiatives/INIT-XXXX-modernization.md"
  stage_specs: [] # пути к реально созданным каталогам SPEC, не список всех будущих этапов
  active_spec: null # путь из stage_specs либо null
  cutover: null # путь к операции, когда применимо
  completion: null # после закрытия: ссылка на итоговые evidence в инициативе
```

Это запись выбранного процесса, не автоматический диспетчер. Примеры placeholders
заменить фактом; ссылки должны существовать, неизвестные значения — null с причиной
в assessment. source.commit фиксирует baseline и не переписывается после каждого
этапа; новый запуск сравнивает исходник, текущий HEAD и незакоммиченные изменения.
SHA и evidence этапов находятся в verification.md соответствующих SPEC.

## Состояние

- `assessed`: сохранён аудит, целевое решение ещё не принято.
- `planned`: выбран scope/стек, подготовлен план и первый этап.
- `in_progress`: разрешённый этап выполняется.
- `validating`: реализация scope готова, выполняются итоговые проверки/переключение.
- `blocked`: конкретная внешняя зависимость/решение мешает продолжению, причина и
  условие выхода записаны в инициативе; наличие сложной работы не является блокером.
- `paused`: пользователь отложил работу; записаны точка остановки и следующий шаг.
- `completed`: выполнены применимые критерии закрытия из transition.md; completion
  указывает доказательства. active_spec становится null, история stage_specs сохраняется.

Это статусы процесса в engineering.yaml. Статусы самих Markdown-документов остаются
по контракту главы 20 (например, verified), их не заменяют перечисленные значения.
Состояния blocked/paused возвращаются в фактическую фазу после устранения причины
или возобновления. Не повышать статус по одному наличию файлов.

## Возобновление и закрытие

1. Прочитать профиль, инициативу, active_spec, verification/review и текущий Git diff.
2. Проверить, что источник/ветка/worktree соответствуют работе; не перезаписывать
   незакоммиченные изменения и не переключать существующую сессию автоматически.
3. Проверить свежесть evidence после новых изменений. Продолжить незавершённую
   задачу, сохранив номера SPEC/ADR/инициатив; не генерировать дубликаты.
4. При смене целевого стека/scope обновить решение и план, показать влияние на
   выполненные этапы. Исходный baseline сохранить; уже принятый ADR заменить новым.
5. При завершении текущий `profile`, `ui.target.stack`, навыки и команды отражают
   новый фактический стек. source_stack остаётся историей; target_stack не объявляет
   текущее состояние раньше проверки. Не затирать поля других приложений продукта.
6. Для следующей модернизации завершённый блок сохранить в истории инициативы и Git,
   затем завести новый baseline/инициативу. Обычная новая фича не меняет этот блок.

В MANUAL хранить запуск/проверки, в инициативе — порядок этапов и состояние перехода,
в tasks.md — единственный список задач этапа. Не дублировать статусы каждой задачи
в YAML. Фактические назначения моделей и ADE берутся из ai, не копируются сюда.
