# Надёжное бронирование при одновременных запросах

> Учебная инициатива. Запуск зависит от подтверждения [проблемы](../debt/DEBT-0101.md); она ещё не одобрена и не реализована.

## Цель и границы

Сотрудник получает одну подтверждённую бронь либо понятный конфликт. В область входят защита записи, обработка повторов запроса и подготовка существующих данных. Не входят отмена, повторяющиеся встречи и редизайн интерфейса.

```mermaid
flowchart LR
    evidence["Подтвердить гонку"] --> decision["Согласовать ADR"]
    decision --> spec["Уточнить SPEC"]
    spec --> plan["План и задачи"]
    plan --> migration["Подготовить данные"]
    migration --> change["Внедрить защиту"]
    change --> verify["Проверить и закрыть долг"]
```

## Измеримый результат

| Критерий | Доказательство для завершения |
| --- | --- |
| Один слот — одна бронь | Проверка 100 конкурентных запросов и итоговых данных |
| Повтор не создаёт новую бронь | Повтор после потерянного ответа возвращает прежний ID |
| В старых данных нет конфликтов | Отчёт сверки после согласованного разрешения дублей |

Исходные значения не измерены. Цели иллюстрируют критерии, а не результат работы.

## Последовательность и связи

Использовать исходные skills спецификации и планирования: создать SPEC, затем `tasks/plan.md` и задачи в выбранном единственном источнике. Эти документы ещё не созданы, поэтому фиктивных ссылок на них нет. Контрольные точки: подтверждение причины, согласование модели миграции, проверка конкуренции и готовность отката.

Архитектурные входы: [ADR](../decisions/ADR-0101.md), [LLD](../lld/booking.md), [данные](../data/booking.md). Владелец учебного решения — команда бронирования; в продукте требуется реальный ответственный. Это авторский пример связи артефактов, а не отдельный процесс из upstream.
