# Graphify: установка и сопровождение продукта

Обязательно для каждого профиля, включая custom, при init нового репозитория
и подключении платформы к существующему продукту. Установка CLI и навыка —
только начало: настройка завершена после проверки графа и его обновления.
Агент выполняет шаги сам в рамках согласованной настройки. Запрос «только
проверить» разрешает диагностику, но не установку и не изменение хуков.

## 1. Инструмент и область анализа

Проверить `command -v graphify`, `uv tool list`, `graphify --help`.
Отсутствующий CLI установить через `uv tool install graphifyy`; существующий
не обновлять автоматически. Версию CLI записать в MANUAL.md отдельно от SHA
навыка в engineering.yaml. Официальные источники:
[репозиторий](https://github.com/Graphify-Labs/graphify),
[документация](https://docs.graphify.com/), проектный навык graphify.

Из корня продукта определить фактические исходники, тесты, контракты и нужные
документы: README, MANUAL, docs/ с SPEC/HLD/ADR/UI, при необходимости design/.
Не требовать ещё не созданные архитектурные документы при init.
Зафиксировать включённые пути в MANUAL.md. Создать отслеживаемый
`.graphifyignore`, дополняя существующий без потери пользовательских правил.
Базовый список (уточнить реальные пути генерации конкретного продукта):

```gitignore
.canvas/
.agents/skills/
.agents/references/
.agents/agents/
.claude/skills/
.claude/references/
.claude/agents/
.go-product-platform/
graphify-out/
node_modules/
vendor/
.venv/
__pycache__/
dist/
build/
coverage/
.next/
```

Дополнить путями других копий сторонних материалов, сгенерированных Wails,
Protobuf/Connect, sqlc bindings и сборок. Не исключать целиком смешанные
каталоги с рукописным кодом; сохранить исходные .proto, SQL и миграции.
Сторонние команды и адаптеры также исключить по их фактическим путям.
Проверить итоговый список обнаруженных файлов: нужное входит, шум исключён.
`.gitignore` учитывается дополнительно; не применять `--no-gitignore` без
разбора причин. Одна `.graphifyignore` действует для extract, update, watch
и хуков; при смене области анализа повторно проверить состав и пересобрать граф.
В `.gitignore` продукта сохранить `/graphify-out/`.

## 2. Первоначальный граф

После подготовки кода и документации выполнить полный цикл проектного навыка
`/graphify .`, включая семантический анализ выбранных документов. Это команда
навыка в ADE, а не shell-команда. Headless-вариант при настроенном разрешённом
LLM backend: `graphify extract .`, затем `graphify cluster-only . --no-label`
и `graphify export html`. Не записывать ключи в репозиторий.

`graphify extract . --code-only` подходит для диагностики AST, но не заменяет
полную сборку, если в области анализа есть документация или изображения.
Если семантический анализ недоступен, явно отметить неполную настройку.
Проверить graphify-out/graph.json, GRAPH_REPORT.md, graph.html, наличие
ожидаемых файлов/символов и запрос `graphify query "<реальный символ>"`.
Пустой каркас без поддерживаемого кода анализировать по имеющимся документам;
не создавать фиктивное приложение ради успешного чек-листа.

## 3. Git-хуки и Canvas

До установки проверить `git config --show-origin --get core.hooksPath` и
`git rev-parse --git-path hooks`, содержимое и executable-бит существующих
post-commit, post-checkout, post-merge, post-rewrite. Отсутствие core.hooksPath
нормально. Сохранить резервные копии изменяемых хуков вне отслеживаемых файлов.

```sh
graphify hook install
graphify hook status
```

Проверенная версия 0.9.111 устанавливает все четыре перечисленных хука и
merge driver; проверить также diff .gitattributes и локальную Git-конфигурацию.
Не предполагать, что любая версия поддерживает все события. Хуки не покрывают
произвольные изменения рабочего дерева и не заменяют семантический анализ.

Установщик дописывает блок к существующему хуку. Если предыдущий обработчик
Canvas завершает скрипт через exit/exec, блок Graphify недостижим. В таком
случае сохранить исходный обработчик отдельным исполняемым файлом и организовать
общий dispatcher: вызвать оба обработчика с исходными аргументами и stdin
(для post-rewrite вход нужно сохранить и передать обоим), сохранить исходный
код ошибки Canvas. Не перемещать обработчик вслепую: проверить его относительные
пути и окружение. Не заменять чужой hook manager и не сбрасывать core.hooksPath.
Если путь общий для других репозиториев, не менять его без разбора области
действия; установка в неиспользуемый .git/hooks не считается успехом.

Повторить установку и убедиться, что нет дубликатов. Проверить реальное
выполнение обоих обработчиков. После установки/обновления Canvas повторить
проверку: его установщик может поменять хуки. В новом worktree проверить
эффективный путь хуков и локальность graphify-out/; не считать общие хуки
доказательством наличия локального графа.

## 4. Инструкции агента

Выполнить `graphify agents install`, если команда есть в help установленной
версии. В 0.9.111 используется `graphify codex install` — она пишет AGENTS.md.
Не запускать неизвестную команду вслепую: CLI может напечатать usage без ошибки.
Проверить реальный diff. Сохранить пользовательские правила, блок GPP и
служебные маркеры Graphify; внутри обслуживаемого раздела согласовать русские
правила с разделом Graphify из примера AGENTS.md платформы. Оставить один раздел,
без дублирования. После повторной установки проверить и снова согласовать
текст, если CLI восстановил стандартный блок. CLAUDE.md ссылается на AGENTS.md.

Перед анализом зависимостей агент проверяет наличие графа, изменения исходников
и документов относительно последней сборки (manifest/состояние Graphify,
изменённые, новые и удалённые файлы), pending-маркеры, а не только время файла
или чистоту git status. `graphify check-update .` проверяет семантический флаг,
но сам по себе не доказывает актуальность всего графа.
Устаревший код обновить через `graphify update .`; документы — полным
семантическим циклом `/graphify . --update`. Сначала query/path/affected для
зависимостей, затем проверка исходников; INFERRED не является доказательством.
При недоступности инструмента — точечный rg и явное сообщение об ограничении.

## 5. Разработка до коммита

```sh
graphify watch .
```

Запускать из корня продукта рядом с dev-процессом, один watcher на дерево;
остановка — Ctrl+C или через процесс-менеджер dev-команды. Записать конкретный
способ запуска/остановки в MANUAL.md. Watcher автоматически обновляет AST кода.
Для документов и изображений он лишь отмечает необходимость семантического
обновления: в 0.9.111 это graphify-out/needs_update. Выполнить
`/graphify . --update` по навыку (либо настроенный полный headless extract).
Не удалять pending-маркер вручную ради «готовности». Учитывать также маркеры
версии навыка, например .needs_update. Не оставлять code-only режим настройкой
полного графа: он исключает семантические файлы из последующей обработки.

## 6. Приёмка и восстановление

В отдельном временном Git-репозитории с настройками продукта проверить:

1. Первоначальный граф содержит нужный код и документацию, исключения работают.
2. Добавление реальной функции и вызова меняет узлы и связи после commit;
   существующий обработчик Canvas продолжает выполняться.
3. Checkout, merge и rewrite проверяются для заявленного набора событий.
4. Watcher видит изменение кода до коммита; изменение документа создаёт pending,
   семантическое обновление отражает новый смысл и снимает необходимость обновления.
5. Повторная установка не дублирует хуки и не теряет пользовательские инструкции.
6. Новый worktree использует свой граф; исключения сохраняются после обновления.

Не создавать пробные коммиты в пользовательской ветке. Фиксировать фактически
выполненные проверки и ограничения в MANUAL.md; не выдавать имитацию Canvas
за проверку его реального обработчика.

При отсутствии/повреждении графа сохранить старый graphify-out/ вне области
анализа, проверить CLI, область анализа и выполнить первоначальный полный цикл.
При устаревшем коде — `graphify update .`; при документах — семантический update.
Если защита от уменьшения графа отказала, сначала проверить исключения и удаления;
`--force` использовать только после подтверждения ожидаемого уменьшения.
При неработающем хуке проверить эффективный hooksPath, права, PATH/interpreter,
ранний exit и состояние hook status; восстановить композицию из резервной копии,
переустановить только блок Graphify и повторить функциональную проверку.
После переноса clone/worktree заново определить локальный interpreter и корень;
не копировать абсолютные пути из чужого graphify-out/.

## Проверка инструкции платформы

На 2026-11-23 с CLI graphifyy 0.9.111 в отдельном временном Git-репозитории
фактически проверены:

- AST-сборка Python-кода; исключение .canvas/, .agents/ и bindings/.
- Добавление функции и вызова через commit: узел и связь появляются в query.
- Сохранение исполняемого существующего post-commit с контрольной записью;
  повторный hook install оставляет его содержимое неизменным.
- Два запуска codex install сохраняют пользовательский текст AGENTS.md.
- Watcher добавляет функцию до коммита; новый Markdown создаёт needs_update.
- Checkout удаляет символ другой ветки, merge возвращает его; amend обновляет граф.
- Отдельный worktree строит свой граф; локальный символ не попадает в основное дерево.
- cluster-only с --no-label --no-viz создаёт GRAPH_REPORT.md.

Это проверка механизма на минимальном примере, не приёмка конкретного продукта.
Реальный Canvas заменён контрольным обработчиком без раннего exit; сложный
dispatcher, внешний hooksPath и rebase отдельно не проверялись. Amend проверен
как Git-операция, без изоляции post-rewrite от post-commit. Полное семантическое
извлечение документов/изображений с LLM и снятие pending после него не запускались.
При настройке продукта выполнить недостающие проверки из раздела приёмки.
