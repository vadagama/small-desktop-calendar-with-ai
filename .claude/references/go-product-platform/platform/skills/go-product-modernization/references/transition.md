# Этап, переключение и завершение

## Реализация этапа

1. Проверить исходную ревизию и локальные изменения. Зафиксировать baseline
   сохраняемых контрактов; команды/evidence записать в verification.md.
2. Изолировать старую и новую реализацию: процессы, порты, тестовые данные и
   зависимости. Согласовать владение API/БД; временные адаптеры имеют владельца
   и условие удаления. Не создавать обязательный универсальный каталог new/legacy.
3. Реализовать срез в рамках SPEC. Сохранить исходники контрактов и маршруты,
   требующие совместимости; изменяемые контракты явно версионировать по решению.
4. Выполнить проверки нового кода и сравнение сценариев с baseline, ошибки/повторы,
   права и целостность данных. Для UI — работающий рендер, доступность и сценарии;
   для native/desktop — фактическая целевая платформа.
5. Независимое ревью фиксирует замечания, решения и SHA проверенной реализации.
   Изменения после проверки требуют соответствующей повторной проверки.
6. Обновить HLD/MANUAL по реально работающему состоянию. Закрыть этап только
   по его AC; оставшиеся этапы и старые компоненты остаются явно обозначенными.

На этапе можно развивать уже перенесённую часть обычными SPEC, сохраняя временные
границы совместимости. Статус всей модернизации при этом не completed.

## Данные и переключение

Этот раздел нужен только если этап меняет эксплуатацию или данные. Для чистого
рефакторинга без deploy достаточно регрессионных проверок и обычного выпуска.

План cutover должен задавать:

- исходную/целевую версию приложения и схему данных;
- backup и фактически проверенный способ восстановления в изолированном окружении;
- совместимость на период перехода, обработку записей во время переноса;
- rehearsal на допустимых тестовых/обезличенных данных и проверки потерь/дубликатов;
- порядок действий, владельца, требуемые разрешения, окно и критерии go/no-go;
- мониторинг после переключения и измеримые условия остановки;
- откат приложения **и данных**, ограничения обратимости и точку невозврата;
- условие/период завершения наблюдения и удаления прежней реализации.

Смена бинарника не откатывает несовместимую миграцию данных. Для необратимых
операций нужны явно выбранный recovery-путь и разрешение на конкретное действие.
До production-переключения выполнить все доступные подготовительные проверки и
представить конкретный план. Без авторизации завершить подготовку и честно отметить,
что переключение не выполнено. Не объявлять dev-rehearsal production-результатом.
При сбое остановить переключение, выполнить разрешённый recovery-план, сохранить
диагностику; не повторять разрушительные операции без выяснения причины.

## Закрытие всей модернизации

Проверить применимость каждого пункта, указать доказательство либо причину N/A:

| Критерий | Доказательство |
|---|---|
| Scope выполнен | Все принятые этапы/AC закрыты; исключения явно приняты и ограничены |
| Поведение сохранено | Сценарные/контрактные проверки, реальные интеграции и права |
| Данные корректны | Результаты переноса/сверки и восстановления, если был перенос |
| Новый стек основной | Команды запуска, build/test, CI/CD, deployment и поддерживаемые ОС |
| Эксплуатация готова | Наблюдение завершено по принятому условию, cutover и recovery проверены |
| Старый путь завершён | Активные вызовы/зависимости удалены после окна отката либо оставлены только вне scope |
| Документы и инструменты актуальны | HLD, MANUAL, engineering.yaml, AGENTS/CLAUDE, skills и ADE-адаптеры |

Пока продукт ещё зависит от заменяемой реализации внутри scope или требуется
непроведённое переключение, переход остаётся активным. План с исключёнными
компонентами не даёт права назвать весь продукт перенесённым: перечислить остаток.
Рефакторинг на том же стеке завершается без выдуманного этапа смены технологий.

При завершении обновить текущий профиль и навыки под фактический стек. Навыки
старого стека удалять только если больше не нужны другим компонентам; не менять
глобальные копии автоматически. Назначения ai сохранять либо менять по согласованной
перенастройке. Инициативу и SPEC закрыть по контракту, историю и baseline сохранить.
Следующие функции выполняются через обычный SDD; повторная модернизация — новая
инициатива с собственной исходной ревизией.
