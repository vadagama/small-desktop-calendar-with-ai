# SDD для AI-агентов: соло и команда 3–5 человек

<a name="sdd-v17"></a>

## Процесс как руководство

Платформа задаёт последовательный процесс, а не только каталог навыков.
**Одна фича — один владелец, одна спецификация и отдельное рабочее дерево Git.**
Фича проходит путь от пользовательского сценария через API/домен/данные до E2E.
Человек определяет результат, пределы автономии и принимает риск; агент выполняет
согласованную работу и предъявляет доказательства.

С v17 этапы и условия готовности — это процесс разработки,
проектные полномочия (`docs/agent-policy.md`) и главы 19–20 руководства, а не исполняемые ворота CLI. Команды `sdd-*` и модуль
`installer/sdd.py` удалены: артефакты — обычный Markdown с YAML frontmatter (глава 20),
и агент правит их свободно, но честно. Дисциплину обеспечивают инструкции агенту,
свежие проверки, независимое ревью и Git-история. Это осознанный обмен: меньше
механики для поддержки — больше ответственности на людях и ревью. Если проекту
нужен обязательный контроль, вводите его средствами CI и защищённой ветки.

Три слоя не смешиваются:

| Слой | Содержание | Где живёт |
|---|---|---|
| Процесс | SDD, планирование, TDD, ревью, работа с контекстом | Проектные навыки + правила продукта |
| Технологии | Go, Buf/Protobuf, Connect, PostgreSQL, React, Wails, Playwright | Выбранные проектные навыки |
| Продукт | HLD, технические решения SPEC, ADR, контракты, SPEC, задачи, долг, инициативы | Markdown с YAML frontmatter в Git продукта |

Upstream `addyosmani/agent-skills` не форкается и не переписывается. Расширенный
каталог и профили включают инженерные навыки (в том числе `spec-driven-development`
и `test-driven-development`). Полная настройка после согласования включает
установку недостающих источников и проектных копий; создание одних документов
не завершает настройку. Существующий выбор навыков при миграции сохраняется,
добавление обязательной основы согласуется в плане.

`docs/agent-policy.md` фиксирует только проектные исключения: его полномочия
и границы имеют приоритет в продукте, универсальный процесс не дублируется.
Навыки загружаются по задаче;
не следует загружать всю коллекцию. Это не разрешение обходить неудачные тесты,
пользовательские ограничения или контроль высокого риска.

<a name="sdd-gates"></a>

## Последовательные этапы и условия готовности

```text
specify → design → plan → implement → verify → review → ready → released
    ↑          изменение утверждённых входов: новый цикл       |
    └────────── требования/дизайн/план пересогласовываются ─────┘
```

| Текущий этап → следующий | Условие готовности (проверяет человек/ревью, не CLI) |
|---|---|
| specify → design | Цель, сценарии, границы, уникальные AC-ID и оценка влияния заполнены; SPEC принят |
| design → plan | Дизайн принят: решение, данные/контракты, риски и альтернативы |
| plan → implement | План и задачи приняты; уникальные T-ID, ациклические зависимости, ссылки на AC; зависимые фичи готовы |
| implement → verify | Все задачи закрыты; каждый срез прошёл модульную проверку |
| verify → review | Свежие unit + E2E и дополнительные проверки; каждый AC отражён в отчёте; затронутые документы заполнены |
| review → ready | Ревью другой сессии, вердикт pass, ноль блокеров; код и проектные документы зафиксированы в Git |
| ready → released | Явное решение человека и фактический выпуск во внешней системе |

Не перепрыгивайте этапы, не принимайте пустые шаблоны, не продолжайте после
изменения согласованных требований/дизайна/плана/состава задач — начните новый
цикл с пересогласования и заново пройденных проверок.

`status: "accepted"` у документа означает, что ответственная сторона проверила
его содержание; это не автоматическое утверждение человеком. Для low/medium
в согласованном объёме это может сделать агент. Для high нужен реальный человек.
Инструкции не способны доказать, что текст осмыслен: ревью должно сопоставить
требования, реализацию, тесты и документы.

<a name="sdd-autonomy"></a>

## Риск, автономия и изменение объёма

| Класс | Примеры | Правило |
|---|---|---|
| low | Обратимая локальная правка без смены контрактов | Агент проходит этапы внутри запроса |
| medium | E2E-фича в существующих границах, совместимый API | Агент готовит и проверяет SPEC/дизайн/план; человек доступен для существенной неоднозначности |
| high | Разрушительная миграция, смена модели доступа, границ доверия или архитектуры | Человек принимает требования, дизайн и план до реализации |
| выпуск | Изменение рабочей среды | Отдельное явное разрешение независимо от класса |

Для high решение о переходе к design, plan и implement принимает человек;
ссылку на решение фиксируйте в PR/журнале фичи. Агент не выдумывает одобрения
и не понижает класс риска ради темпа.

Принятый объём не расширяется молча. Новая идея — раздел отложенного объёма,
долг или новая спецификация. До поставки изменение согласованных входов означает
новый цикл: перепишите затронутые документы, перечитайте проверки и пройдите
этапы заново; прежние результаты храните в истории фичи. После выпуска создавайте
delta-spec с новым ID и ссылкой `related` на исходную SPEC; актуальную архитектуру
обновляйте по результату.

Маленькая правка не требует длинного документа: обязательные разделы могут быть
краткими. Для чисто документальных изменений выполняйте обычное ревью — не
имитируйте E2E приложения там, где его нет.

<a name="sdd-example"></a>

## Полный сценарий E2E-фичи

Пользователь: «Добавь назначение планограммы нескольким магазинам. Сделай API,
домен, хранение и интерфейс. Проверь права, повтор команды и пользовательский путь».
Агент сначала читает AGENTS, agent-policy (если создан), релевантные HLD, технические решения SPEC и контракты, затем создаёт
документы фичи:

```sh
# Документы фичи создаёт агент по шаблонам главы 20:
# docs/specs/SPEC-assignments/:
# requirements.md → design.md → plan.md → tasks.md
```

Заполнить `requirements.md`: сценарий пользователя, отрицательные сценарии,
пределы объёма; `acceptance_ids: ["AC-01", "AC-02"]`; критерии должны быть в тексте.
`affected_docs` перечисляет ID действительно затронутых документов. По умолчанию
там HLD-product: перед первой фичей его нужно заполнить. Для локальной правки
можно указать пустой список, но объяснить отсутствие влияния в SPEC и проверке.
Затем `design.md` — решение и альтернативы (обновить затронутые HLD/ADR и исходники контрактов/схем),
`plan.md` — порядок вертикальных срезов, `tasks.md` — задачи.

Задачи — вертикальные срезы: сначала назначение одному магазину с проверкой прав,
затем массовое назначение с идемпотентностью и UI. Не разбивать фичу на отдельные
независимые очереди «вся БД», «весь backend», «весь frontend».

Пример метаданных и тела `tasks.md` (остальные общие поля сохраняются):

```yaml
task_ids: ["T-01", "T-02"]
task_dependencies: ["T-02:T-01"]
```

```markdown
## Задачи

- [ ] T-01 Назначение одному магазину: AC-01; проверить go test ./internal/assignments/...
- [ ] T-02 Массовое назначение и UI: AC-02; проверить pnpm exec playwright test assignments.spec.ts
```

Агент работает по зависимостям и после каждого среза запускает реальные проверки;
команды отмечает в tasks/verification. Команды приложения — примеры; агент
использует реальные команды продукта.

```sh
go test ./internal/assignments/...
pnpm exec playwright test assignments.spec.ts
# При изменениях API — проверка контрактов:
buf breaking --against '.git#branch=main'
```

**Финальные** unit/E2E должны запускаться после фиксации исходников и документации
в Git: свежий кандидат — это закоммиченное состояние, а не рабочее дерево с
незаконченными правками. В verification.md для каждого AC записывается конкретный
тест и результат; здесь же объясняется обновление затронутых документов.

Ревьюер другой сессии читает SPEC, diff, результаты и затронутую архитектуру.
В `review.md` записывает `reviewer`, разные `reviewer_session` и
`implementer_session`, `verdict: "pass"`, `blockers: 0`; в теле — выводы,
проверенные файлы и ограничения. Это должна быть реальная отдельная проверка,
а не смена имени у того же исполнителя.

Готовность и выпуск не выполняются командами платформы. Слияние — через обычный
процесс PR/защищённой ветки. Выпуск — отдельный процесс с разрешением, подписанием,
базовыми проверками, восстановлением и журналом поставки; этап released фиксирует
фактическое решение человека и внешнее подтверждение, а не сам deploy.

<a name="sdd-evidence"></a>

## Доказательства и свежесть

Проверка — это реально исполненная команда, а не утверждение об успехе. Успех —
нулевой exit code на актуальном кандидате; ошибка, таймаут или сбой запуска —
тоже результат, его не прячут. Для каждого вида проверки учитывается **последняя**
запись, а не любая успешная.

Хеш кандидата — состояние отслеживаемых и неигнорируемых новых файлов, удалений,
исполняемого бита и подмодулей. Исключение — последующий коммит только с отчётами
verification/review и ссылками на результаты, без изменения проверяемых входов.
В отчёте сохраняется SHA проверенного кандидата; новый SHA не объявляется проверенным.
Смена исходников, требований, плана, дизайна, архитектуры или ребазирование требуют
актуальных проверок. Сырые журналы лежат в игнорируемом каталоге; в Git — команда,
результат и ссылка на журнал. Для передачи между машинами приложите журнал
к PR/CI без секретов: сам Markdown не содержит полной трассировки теста.

Инструкции не доказывают, что команда `true` тестирует приложение. Соответствие
теста критерию и достаточность покрытия проверяет независимый рецензент; обязательный
CI должен запускать доверенные команды продукта, а не принимать произвольный текст.

<a name="sdd-team"></a>

## Соло, команда и интеграция

**Соло:** человек — владелец продукта; основной агент реализует вертикальную фичу,
другая сессия/модель проверяет её в отдельном контексте. Отсутствие коллеги не
отменяет независимое ревью. Ревью можно выполнить последовательно, без постоянного
запуска нескольких агентов и без лишней нагрузки на локальную машину.

**Команда 3–5 человек:** каждый человек отвечает за E2E-фичу и своих агентов.
Общие API, миграции и межмодульные интерфейсы согласуются до параллельной реализации.
`depends_on` в SPEC содержит ID предшествующих фич; до implement они должны быть
ready/released. ID выбираются устойчивыми и уникальными, например
SPEC-assignments-bulk, ADR-assignments-idempotency; числовые ID допустимы, но
выделяются согласованно, а не одновременно несколькими агентами.

Один пишущий агент на фичу/worktree. Процесс не является распределённой
блокировкой и не поддерживает конкурентную запись одной фичи. БД, порты, файлы,
скриншоты и процессы изолируются по рабочим деревьям. Сначала сливаются поставщики
контрактов, затем потребители; финальный кандидат проверяется после интеграции.
Старый зелёный отчёт до ребаза не считается доказательством нового кандидата.

<a name="sdd-enforcement"></a>

## Граница контроля и миграция

С v17 в платформе нет машинного валидатора артефактов и ворот переходов.
Контракт frontmatter — конвенция: соблюдайте её, чтобы документы разбирались
простыми инструментами и ревью не тратило время на разнобой формата. Если проекту
нужна обязательная проверка формата или готовности — добавьте собственные проверки
в CI продукта (формат frontmatter, уникальность ID, существование ссылок, реальные
тесты) и включите их как required checks защищённой ветки. Файлы доступны
пользователю: никакой инструмент платформы не защищает от намеренной подделки,
а запрет прямого push задаёт Git-хостинг. Платформа не заявляет обратного.

Инициализация структуры выполняется агентом при настройке продукта:
добавляются только отсутствующие декларации `product.yaml` и `engineering.yaml`,
`docs/README.md` и `docs/agent-policy.md` — только при наличии проектных
исключений; существующие документы, пользовательские разделы
AGENTS/CLAUDE и выбор навыков сохраняются. Продукты v18 при обновлении переносят
`docs/workflow.md` → `docs/agent-policy.md` (оставив только исключения),
`docs/agent-skills.md` → `engineering.yaml` в корне. Исключённые каталоги
документации мигрируются с сохранением содержания и ссылок по
[контракту структуры](20-artifact-contract.md#миграция-структуры). Устаревшие
артефакты прежних версий платформы (`state.md`, `gates/`,
`evidence/`, `history/`) остаются как история проекта; новые фичи такие файлы не
создают. Каталоги платформы до v18 (`docs/engineering/`, `docs/architecture/`,
`docs/contracts/`, `docs/specifications/`) переносятся в структуру главы 20 при
обновлении продукта. Старые проектные инструкции нужно согласовать с текущей версией;
автоматически переписывать их нельзя. Если у продукта уже есть система
спецификаций, согласуйте перенос/соответствие форматов; платформа не конвертирует
OpenSpec или чужой YAML.
