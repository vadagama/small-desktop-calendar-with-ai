# Контракт инженерных артефактов

<a name="artifact-layout"></a>

## Целевая структура репозитория

Структура v1.0 — компактная, расширяется по мере необходимости. Каталоги
`proto/`, `db/`, `internal/`, `web/` иллюстрируют Go-стек; при другом стеке
физическое расположение исходников может отличаться.

```text
product/
  README.md                       # вход в продукт
  AGENTS.md, CLAUDE.md            # короткие точки входа для агентов
  MANUAL.md                       # настройка, запуск, проверки
  product.yaml                    # паспорт продукта
  engineering.yaml                # инженерный профиль (замена реестра docs/agent-skills.md)
  landscape.yaml                  # только при подключении корпоративного каталога
  .gitignore
  .agents/, .claude/              # проектные материалы набора, под Git
  .codex/                        # конфигурация/роли, если выбран Codex
  .zed/                          # проектные настройки, если нужны для Zed
  orca.yaml                      # lifecycle-команды, если нужны для Orca
  .opencode/                     # нативные адаптеры, если выбран OpenCode
  opencode.json                  # либо opencode.jsonc, если выбран OpenCode
  prototypes/                    # экспериментальные прототипы
    PROTOTYPE-0001-name/          # отдельный эксперимент, не целевое приложение
    PROTOTYPE-0002-name/
  docs/
    README.md                     # карта документации
    agent-policy.md               # только проектные полномочия и исключения
    hld/README.md                 # HLD; по мере проектирования, не при init
    adrs/                         # один реестр уникальных ADR-ID
    specs/SPEC-0001-name/         # шесть документов фичи
    ui/DESIGN.md                 # единая дизайн-система целевого UI
    ui/SPEC-0001-name/            # vision.md, components.md, screens.md
    debt/                         # подтверждённый технический долг
    initiatives/                  # группы связанных улучшений
    operations/                   # эксплуатация: SLO, мониторинг, восстановление
  proto/, db/migrations/, internal/, web/   # код, контракты, миграции (иллюстративно)
  tests/
  .go-product-platform/           # локальные материалы агента; игнорируется Git
  graphify-out/                   # производный граф кода; игнорируется Git
```

Принцип структуры: **один артефакт — одна ответственность — один источник
истины**. Агент должен однозначно понимать, где искать действующее требование,
где обоснование решения, где реальный контракт и какие проверки доказывают
правильность реализации. Документация делится на четыре группы:

| Группа | Артефакты | Вопрос |
|---|---|---|
| Постоянная архитектура | hld, adrs | Что продукт должен обеспечивать, как он устроен сейчас, какие решения действуют |
| Изменения | specs, initiatives, debt | Что предстоит изменить, зачем, как и с каким результатом |
| Инженерные настройки | product.yaml, engineering.yaml, agent-policy.md | Паспорт, профиль, состав набора, полномочия агента |
| Реализация и проверка | код, proto, миграции, tests, graphify-out | Фактическая реализация и доказательства её правильности |

### Архитектура и технические контракты

HLD — единая логическая модель продукта: контекст, границы, компоненты,
интеграции, развёртывание, безопасность и ключевые NFR. Для маленького продукта
достаточно `docs/hld/README.md`; делить HLD на документы внутри `docs/hld/`
стоит только при реальном росте материала.

Устройство изменяемого модуля, состояния, транзакции и алгоритмы описываются
в `docs/specs/<SPEC>/design.md`. Общие действующие архитектурные ограничения,
семантика API/событий и владение данными отражаются в HLD со ссылками на
первоисточники: Protobuf/OpenAPI, схемы, миграции и код. Долгосрочные решения —
в ADR. Отдельные каталоги для LLD, интерфейсов и данных не создаются.

### Требования и спецификации

Требования и критерии приёмки хранятся в `docs/specs/<SPEC>/requirements.md`.
При завершении фичи они остаются там; переноса в отдельный каталог требований нет.
В `docs/README.md` поддерживается карта актуальных SPEC по возможностям продукта.
При изменении требования новая SPEC ссылается на заменяемое требование прежней,
а карта указывает актуальную версию. История и исходные результаты проверок
сохраняются; карта содержит ссылки, а не вторую копию требований.

### Роль Graphify

`graphify-out/` — производная карта зависимостей для анализа и сверки, не
источник архитектурной истины:

| Источник | Роль |
|---|---|
| HLD / технический design SPEC / ADR | Согласованные архитектурные знания и решения |
| Код / Protobuf / миграции | Фактическая реализованная структура |
| Graphify | Производная карта зависимостей для анализа и сверки |

Если граф показывает зависимость, отсутствующую в HLD, агент проверяет её
значимость и предлагает обновление архитектуры или ADR, а не объявляет любую
найденную зависимость архитектурной автоматически.

### Корневые декларации

`product.yaml` — паспорт продукта:

```yaml
schema_version: "1.0"
name: "orders"
purpose: "Внутренний сервис управления заказами оптовой торговли"
owners: ["oleg"]
stage: "development"
```

`engineering.yaml` — инженерный профиль и единственное место фиксации состава
набора и назначений моделей (замена реестра `docs/agent-skills.md` и lock-файла платформы).
Ниже минимальный фрагмент; полная схема 1.2 с ui и ai —
[engineering.yaml](../templates/engineering.yaml):

```yaml
schema_version: "1.2"
platform:
  source: "go-product-platform"
  revision: "<git-sha ревизии платформы>"
profile: "<go-api | web | desktop | mobile-native | ai | custom>"
policy:
  file: "docs/agent-policy.md"
skills:
  - name: "go-platform-bootstrap"
    source: "<репозиторий>"
    revision: "<git-sha>"
    paths: [".agents/skills/go-platform-bootstrap/", ".claude/skills/go-platform-bootstrap/"]
    purpose: "настройка платформы"
    status: "current"
```

В каждой записи фиксируйте точные пути и SHA; для не-Git источника —
неизменяемую версию или дату снимка вместе с контрольной суммой. Ревизии
описывают проектные копии и не меняются от одного лишь глобального обновления.
Версии CLI Graphify и Orca фиксируются в `MANUAL.md` — это не ревизии их навыков.

`landscape.yaml` — связь с корпоративным каталогом; создаётся только при
подключении Enterprise Landscape, иначе не создаётся вовсе.

`docs/agent-policy.md` — только проектные полномочия и исключения: какие
операции агент может выполнять автоматически, какие требуют подтверждения,
какие архитектурные границы запрещено нарушать и какие особые проверки нужны
продукту. Общий процесс SDD, TDD и ревью живёт в референсах процесса разработки
продукта и здесь не дублируется. Если проектных исключений нет, файл не создаётся.
`AGENTS.md` и `CLAUDE.md` — короткие точки входа в эту конфигурацию; десятки
страниц правил в них не копируются.

Корневые yaml-декларации используют то же подмножество значений, что и
frontmatter: ключи snake_case, строки в двойных кавычках, однострочные списки,
JSON-совместимые значения; вложенность допускается по схемам выше и полному шаблону engineering.yaml.
Блоки ui.target, ui.prototypes, ai.roles и ai.assignments описаны в
[UI-контракте](../references/prototyping-installation.md) и
[контракте моделей](../references/model-harness-configuration.md).
Schema 1.2 относится к engineering.yaml; product.yaml сохраняет 1.0.
Schema 1.2 добавляет ai.surfaces/primary_surface и surface назначения;
миграция 1.1 сохраняет роли и уточняет ADE, не угадывая её по харнесу.
[Настройка всех ADE](../references/ade-installation.md) применяется только к выбранным средам.
Отсутствующие блоки старого профиля означают «не настроено», миграция сохраняет
неизвестные пользовательские поля.

Продуктовые репозитории обязаны использовать эту структуру и процесс из
главы 19. Обоснованные адаптации фиксируются в `docs/agent-policy.md` продукта.
При подключении app-canvas его `design/` дополняет эту структуру;
дизайн-спецификации ссылаются на инженерные SPEC, а не создают второй список
задач. Все документы продукта входят в Git. Init создаёт только то, что имеет
предметное содержание (см. «Создание при init»); остальные архитектурные
документы — по необходимости. Это шаблоны, не доказательство выполненной работы.
Служебные каталоги `.go-product-platform/` и `graphify-out/` игнорируются Git;
снимок платформы под `.agents/` и `.claude/` отслеживается и переносится по
[правилам упаковки](../references/platform-installation.md#переносимый-набор-платформы).

## YAML frontmatter v1

```yaml
---
id: "ADR-assignments-idempotency"
kind: "adr"
status: "accepted"
owner: "oleg"
related: ["SPEC-assignments", "HLD-product"]
level: "lld"
module: "assignments"
supersedes: "ADR-assignments-original"
---
```

Области уникальности ID: ID документа (REQ, SPEC, ADR, DEBT, INIT, LLD, HLD)
уникален во всех активных артефактах репозитория; AC-ID и T-ID уникальны внутри
своей SPEC и цитируются как `SPEC-0001/AC-001`. Не переименовывайте ID при
смене заголовка. `related` содержит существующие ID, `depends_on` — направленные
зависимости без циклов, `supersedes` — ID прежнего решения. Уберите supersedes,
если замещения нет.

Поля `id`, `kind`, `status`, `owner`, `related` обязательны. Разрешены дополнительные
плоские поля. Поддерживается **ограниченный YAML 1.2**: ключи в snake_case,
строки в двойных кавычках, числа, true/false/null, однострочные списки строк.
Значения должны быть JSON-совместимы. Вложенные mappings, блочные строки, YAML aliases,
некавыченные даты и многострочные списки не используются: держите frontmatter в этом
подмножестве, чтобы документы разбирались простыми инструментами и оставались
читаемыми. Сложное содержание размещается в Markdown.

Типы: policy, requirement, hld, lld, adr, api, data, event, debt, initiative,
spec, design, plan, tasks, verification, review, registry, manual, operation.
Статус `draft` допустим при создании; рабочий инженерный документ — `accepted`,
`implemented` или `verified`, без TODO/TBD/FIXME в принятых разделах. Для реестра
(`registry`) и инструкции эксплуатации (`manual`) допустим `current`: содержание
заполнено и сверено с фактом. Живое требование (`requirement`) и эксплуатационный
документ (`operation`) поддерживают `current`, пока соответствуют факту.
Шаблоны создаются с `draft`; статус меняется только после заполнения и проверки.

ADR имеют собственный жизненный цикл: `proposed`, `accepted`, `rejected`,
`superseded`. Принятое решение не переписывается задним числом: существенный
пересмотр оформляется новым ADR со `supersedes`, а прежний переводится в
`superseded`.

Контракт распространяется также на корневой `MANUAL.md`. Материалы внешних навыков
и снимок платформы под `.agents/` и `.claude/` сохраняют собственные схемы метаданных.
Служебные типы state/gate/evidence встречаются только в проектах, мигрировавших
с v16; этап процесса теперь описывается в документах фичи, а не отдельным state-файлом.

Следите за целостностью Markdown-ссылок на локальные файлы и ID-связей на ревью;
HTTP-ссылки не проверяются автоматически. Чужие документы в этих каталогах должны
быть приведены к контракту; иные каталоги документации не берутся под управление
автоматически. Исторические циклы исключены из требования уникальности активных ID.

## Когда создавать и обновлять артефакт

| Вид | Содержание | Триггер |
|---|---|---|
| Требования SPEC | Требования, AC-ID, источник в requirements.md фичи | Создание или изменение фичи; обновление карты актуальных SPEC |
| HLD | Контекст, компоненты, интеграции, развёртывание, безопасность, NFR | Изменение границ продукта, платформы, доверия, размещения |
| Технический design SPEC | Ответственность, интерфейсы, состояния и транзакции в design.md фичи | Изменение внутреннего устройства модуля |
| ADR | Контекст, решение, альтернативы, последствия | Долгосрочный выбор с существенными компромиссами |
| API | Контракт в исходниках; общая семантика в HLD, изменение в design.md SPEC | Изменение внешнего/межмодульного контракта |
| Данные | Схема и миграции; владение в HLD, изменение в design.md SPEC | Изменение модели данных или её жизненного цикла |
| События | Контракт в исходниках; гарантии в HLD, изменение в design.md SPEC | Новые события, иной порядок или гарантия доставки |
| Debt | Наблюдение и доказательства, последствия, варианты решения | Подтверждённая проблема, которую не устраняют сейчас |
| Initiative | Цель/эффект, объём, порядок реализации | Несколько связанных изменений с общей целью |
| Operations | SLO, мониторинг, восстановление | Приближение к production, изменение эксплуатации |

Создавайте документы с frontmatter по их ответственности: требования и
техническое решение — в инженерной SPEC, общую архитектуру — в HLD, решения —
в ADR, эксплуатацию — в `docs/operations/`. ID документа уникален в активных
артефактах репозитория. API, события и данные не требуют отдельных Markdown-файлов:
документируйте смысл и ограничения в HLD/SPEC рядом со ссылками на первоисточники.

```text
docs/specs/SPEC-0001-assignments/requirements.md
docs/specs/SPEC-0001-assignments/design.md
docs/hld/README.md
docs/adrs/ADR-assignments-idempotency.md
docs/debt/DEBT-legacy-retries.md
```

Принятый ADR — история решения. Изменение решения создаёт новый ADR с supersedes;
не переписывайте прежнее обоснование. HLD описывает текущее подтверждённое
состояние; design.md SPEC — изменение, его статус и границы реализации. Существование supersedes и
неизменность истории ADR проверяются по diff на ревью.

Protobuf — первоисточник API, миграции и схема — первоисточник данных. Markdown
хранит смысл, ограничения и решения, не дублирует все поля схемы. Для каждой фичи
в SPEC перечисляются affected_docs; verification объясняет, что обновлено и почему.
Изменение одного обработчика не должно переписывать весь HLD.

### Создание при init

Инкрементальная документация: агент создаёт не все возможные документы, а только
то, что уже имеет предметное содержание. Пустые каталоги и фиктивные записи не создаются.

| Артефакт | При init | Позже |
|---|---|---|
| `product.yaml`, `engineering.yaml` | создаётся | актуализируется при смене профиля или набора |
| `docs/README.md`, `AGENTS.md`, `CLAUDE.md`, `MANUAL.md` | создаётся | поддерживается |
| `docs/hld/README.md` | не создаётся при init | по мере проектирования |
| `docs/agent-policy.md` | только при наличии проектных исключений | по необходимости |
| `landscape.yaml` | только при подключении корпоративного каталога | при изменении корпоративных зависимостей |
| ADR | не создаются пустыми | при появлении архитектурных решений |
| SPEC | при запуске разработки функции | по изменениям |
| docs/ui/DESIGN.md и docs/ui/<SPEC>/ | при начатой разработке целевого UI, с содержанием | обновляются вместе с UI; [шаблоны](../templates/ui/README.md) |
| prototypes/PROTOTYPE-NNNN-slug | только для конкретной гипотезы | эксперимент, результат и перенос решений |
| ai в engineering.yaml, адаптеры харнесов | выбор семи ролей и проверка запусков | перенастройка управляющим навыком |
| debt, initiatives | не создаются фиктивными записями | при обнаружении |
| operations | минимальный раздел при необходимости | до production |
| .graphifyignore | область анализа продукта, отслеживается Git | актуализируется при изменении структуры |
| graphify-out | первоначальный граф обязателен; [интеграция](../references/graphify-installation.md) | локально обновляется при разработке и Git-операциях; документы требуют семантического обновления |

### UI/UX и прототипы

`docs/ui/DESIGN.md` задаёт общую дизайн-систему. Для UI-фичи каталог совпадает
с инженерной SPEC: `docs/ui/SPEC-0001-bootstrap/` содержит vision.md (видение),
components.md (компоненты), screens.md (экраны и сценарии). Это дополнение к шести
инженерным документам, без отдельного backlog и отдельной нумерации SPEC.
Каждый UI-документ имеет собственный уникальный ID и kind design;
связи и шаблоны — в [UI-контракте](../references/prototyping-installation.md#документация-целевого-ui).

Эксперименты `prototypes/PROTOTYPE-NNNN-slug/` нумеруются независимо, хранят гипотезу и
результат в README. Их стек един для экспериментов продукта, но может отличаться
от целевого. Для проверки идеи не требуется фиктивная инженерная SPEC;
она появляется при переносе принятого решения в продукт. В Git хранятся исходники,
документы и lockfile, а не node_modules/build/runtime экспериментальных приложений.

### Шесть артефактов SPEC

Набор фичи — шесть документов в `docs/specs/SPEC-0001-name/`. Это шаблоны,
не доказательство выполненной работы.

| Файл | Назначение |
|---|---|
| requirements.md | Цель, scope, действующие требования, AC-ID, ограничения |
| design.md | Предлагаемое решение, варианты, последствия, затронутые компоненты и ADR |
| plan.md | Последовательность вертикальных срезов, зависимости, стратегия реализации |
| tasks.md | Конкретные T-ID, проверки, исполнение или ссылки на внешний трекер |
| verification.md | Матрица AC → тест → результат, ссылки на CI и иные доказательства |
| review.md | Независимое ревью, критичные замечания, принятые решения и блокеры |

Два правила:

- `plan.md` описывает порядок и стратегию реализации, `tasks.md` — исполнимые
  действия; они не дублируют друг друга.
- Если задачи ведутся во внешнем трекере (Linear, Plane, GitLab Issues), `tasks.md`
  служит индексом ссылок на задачи. Источник истины объявляется в
  `docs/agent-policy.md`; статусы не дублируются, авторитетен один список.

Трассируемость фичи: REQ → AC → T → реализация и тесты → подтверждение в
verification и независимом ревью. AC-ID и T-ID цитируются как `SPEC-0001/AC-001`.

<a name="artifact-debt"></a>

## Долг, инициативы и единый список задач

Наблюдение → доказательство → DEBT → при необходимости INIT → SPEC → задачи →
реализация → проверки → закрытие долга. Маленький долг может сразу получить одну
SPEC; не каждому DEBT нужна инициатива. Недоказанный риск — исследование, а не
подтверждённый дефект. Принятый риск требует ответственного, причины и условия
повторного рассмотрения; закрытие долга — ссылки на реализацию и доказательство.

Обязательные метаданные связей:

| Артефакт | Минимальные обязательные метаданные |
|---|---|
| DEBT | ID, статус, проблемный компонент, подтверждающие свидетельства, риск, решение, связанные задачи |
| INIT | ID, цель, причина, ожидаемый результат, scope, приоритет, связанные долги и спецификации |
| ADR | ID, статус, контекст, решение, последствия, связанные модули и supersedes |
| SPEC | ID, статус, требования, acceptance criteria, затронутые архитектурные объекты |

Одна инициатива может закрывать несколько связанных долгов; не каждый долг
превращается в инициативу.

По умолчанию tasks.md — единственный список исполнения. Ссылки на Linear/Plane/
GitLab допустимы в теле или метаданных, но платформа не синхронизирует внешние статусы.
Если позже выбирается внешний источник задач, потребуется отдельный адаптер и
явное изменение контракта; нельзя одновременно считать оба списка авторитетными.

<a name="artifact-validation"></a>

## Проверки

**Конвенциональный (по желанию проекта):** синтаксис frontmatter, обязательные поля,
уникальные ID, существование ссылок, ацикличность зависимостей. В дистрибутиве нет
валидатора; при необходимости добавьте собственную проверку в CI продукта как
required check. Проверка формата не означает приёмку фичи.

Ориентир для собственных проверок:

| Проверка | Правило |
|---|---|
| Structural | Обязательные файлы и корректные пути |
| Metadata | Валидный YAML и уникальность ID |
| Traceability | SPEC → AC → задачи → проверки |
| Architecture | HLD и технические решения SPEC не противоречат принятым ADR |
| Contracts | Разделы HLD/SPEC об API и данных связаны с реальными контрактами |
| Landscape | Продукт связан с существующими корпоративными ID |
| Security | Нет секретов и чувствительных данных в документации |
| Freshness | Указаны актуальность, статус и подтверждения |
| Review | Критичные блокеры закрыты перед merge |
| Drift | Значимые изменения кода отражены в документации |

Для повседневной разработки достаточно быстрых проверок затронутых артефактов;
полный аудит — при merge значимого изменения, релизе либо отдельной проверке
зрелости продукта.

**Смысловой (обязательный):** соответствие HLD и принятых решений SPEC коду, достаточность AC и тестов,
корректность прав/транзакций, достоверность долга, отсутствие противоречащих ADR,
независимость ревью. Рецензент указывает конкретные файлы и выводы; LLM не является
доказательством безошибочности.

## Модернизация продукта

Необязательный блок `modernization` engineering schema 1.2 фиксирует baseline,
исходный/целевой стек, scope и ссылки на этапы. Формат и возобновление —
[контракт профиля](../skills/go-product-modernization/references/profile.md).
Его отсутствие/null не включает процесс; product schema не меняется.

Навык [go-product-modernization](../skills/go-product-modernization/SKILL.md)
использует существующие каталоги: assessment в hld, решения в adrs, программа
в initiatives, этапы в specs, переключение в operations. Артефакты создаются
по выбранному объёму, аудит не порождает пустой комплект SPEC. Подробности —
[обследование и артефакты](../skills/go-product-modernization/references/assessment.md).
После завершения обновляются фактический профиль, HLD и MANUAL; история перехода
сохраняется, следующие функции выполняются обычным SDD.

## Миграция структуры

Продукты v18 переносят при обновлении: `docs/workflow.md` → `docs/agent-policy.md`
(в файле остаются только проектные исключения), `docs/agent-skills.md` →
`engineering.yaml` в корне. Прежние `docs/data/`, `docs/interfaces/`, `docs/lld/`
и `docs/requirements/` исключены из целевой структуры. При миграции сначала
сопоставить их содержимое с HLD, ADR и соответствующими SPEC; сохранить требования,
историю, ID и доказательства, обновить карту docs/README.md и все входящие ссылки.
Нераспределённые материалы сохранить до определения назначения; не удалять
каталоги только по имени. После проверки полноты переноса удалить опустевшие
каталоги. Ссылки в AGENTS/CLAUDE и документах обновляются. Продукты, настроенные до v18, переносят прежние каталоги
(`engineering/`, `architecture/`, `contracts/`, `specifications/`) в целевую
структуру. В проектах, мигрировавших с v16, могут оставаться `state.md`, `gates/`,
`evidence/` и `history/` — это история циклов; новые фичи такие файлы не создают.
