## План реализации: Эталонный путь

| Этап | Результат | Проверка |
|---|---|---|
| 1 | Монорепозиторий Go + чистая доменная модель + сгенерированный Protobuf | Buf/lint/go test |
| 2 | Нативный PG18 + `devctl` изоляция рабочего дерева | Два параллельных API/DB без коллизий |
| 3 | Connect API + веб-приложение React + настольное приложение Wails | Браузерные E2E + базовая проверка настольного приложения |
| 4 | Минимальный Compose на VM + опциональные общие интеграции | Развёртывание на чистой VM + базовая проверка аутентификации и файлов |
| 5 | Офлайн-очередь + проверка концепции синхронизации | Отключение на 24 часа + тесты конфликтов и повторных попыток |
| 6 | Оценка Wails Mobile на устройствах | Все обязательные проверки на устройствах |
| 7 | При неудаче: нативные мобильные приложения Swift/Kotlin | Тесты токенов, аутентификации, SQLite, фоновой работы и push |
| 8 | Опциональный AI SDK + навыки + оценки качества | Проверки безопасности агента и контрактов инструментов |
| 9 | Подписание, учебное восстановление резервных копий, каналы выпуска | Инструкция выпуска и восстановление |

### Минимальная эталонная структура репозитория

```text
product/
├── apps/
│   ├── web/                  # React / Vite
│   ├── desktop/              # Wails 3
│   ├── mobile-wails/         # candidate, can be removed
│   ├── ios/                  # SwiftUI native fallback
│   ├── android/              # Kotlin/Compose fallback
│   ├── api/                  # Go / Connect-Go
│   └── agent-service/        # optional TS AI SDK
├── domain/                   # Pure Go business model
├── application/              # Go use cases
├── adapters/
│   ├── postgres/
│   ├── sqlite/
│   ├── connect/
│   ├── wails/
│   └── objectstorage/
├── proto/                    # Schema source of truth
├── gen/                      # Generated SDKs / type bindings
├── packages/
│   ├── ui/                   # shadcn, tokens, patterns
│   ├── api-client/
│   └── agent-ui/
├── deploy/
│   ├── compose.yaml
│   ├── Caddyfile
│   ├── bao.hcl
│   └── runbook.md
├── tools/devctl/             # Worktree isolation CLI
├── tests/
│   ├── contracts/
│   ├── integration/
│   ├── browser-e2e/
│   ├── desktop-e2e/
│   ├── mobile-device/
│   └── agent-evals/
├── mise.toml
├── buf.yaml
├── buf.gen.yaml
└── AGENTS.md
```

Папки `ios`/`android` допускается не создавать, пока не выбран нативный профиль. `gen/` можно делить на Go/TS/Swift/Kotlin; не смешивать исходники и сгенерированный код. Для большого монорепозитория границы module/import определяются отдельно, но разделение доменной модели Go и адаптера Wails принципиально. Модульная структура внутри `internal/` описана в [архитектуре](02-architecture.md#module-invariants). Структура выше описывает только код; документация, декларации `product.yaml`/`engineering.yaml` и каталоги `docs/` заданы целевой структурой в [контракте артефактов](20-artifact-contract.md).

## Эталонный путь внедрения (v11)

**Этап A — локальный фундамент.** Один шаблон репозитория; Go 1.27.4/PG18.7/mise/pnpm, `make bootstrap/dev/check`, один worktree с нативным PostgreSQL, быстрые модульные/компонентные тесты. Измерить цикл с прогретыми кэшами.

**Этап B — воспроизводимый e2e-фон.** Отдельный проект Playwright для каждого рабочего дерева, наблюдение через watchexec, один процесс Chromium и собственная БД, трассировка и снимок экрана, статус и отметка об устаревании. Сначала 3–5 реальных пользовательских сценариев.

**Этап C — встроенные сервисные возможности.** Добавлять модуль за модулем по реальным требованиям: профили и доступ, аудит, River, FSM, уведомления, аналитика, флаги, поиск. Переиспользуемый реестр модулей времени компиляции, без централизованных микросервисов.

**Этап D — одна финальная проверка перед слиянием.** Зафиксированный кандидат, общий набор `verify`, локальный исполнитель GitLab на Mac для соло-разработки или общий исполнитель в команде, слияние fast-forward, защита main. Перестать дублировать полный прогон в pre-push.

**Этап E — релиз и эксплуатация.** OCI Go + React, минимальный Compose на VM, резервное копирование/PITR, защищённые секреты, общий мониторинг, базовые проверки, откат. Подписание нативных настольных и мобильных приложений — отдельные платформенные проверки. K8s — при измеренной потребности.

**Критерии готовности:** агент может открыть URL worktree, получить тестовый контекст, реализовать изменение, увидеть отрицательный и положительный тест, получить трассировку E2E, предъявить отчет готового кандидата; тот же коммит проходит финальную проверку и поставляется как проверенный артефакт.
