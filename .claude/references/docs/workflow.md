# Процесс разработки

Upstream skills выполняют инженерную работу. Этот документ добавляет входы, выходы и требования к документации. Он не заменяет подробные процедуры навыков и их проверки.

| Этап | Основные skills upstream | Дополнение этого стандарта | Условие завершения |
| --- | --- | --- | --- |
| Контекст | `using-agent-skills`, `context-engineering` | Прочитать конфигурацию, платформу, HLD, активные ADR и текущий план | Известны версии, профиль, ограничения и источник задач |
| Уточнение | `interview-me`, `idea-refine`, `spec-driven-development` | Русская SPEC; карта возможностей для составной инициативы | Критерии проверяемы, scope определён; пройдены применимые согласования upstream |
| Проектирование | `api-and-interface-design`, `documentation-and-adrs`, `constraint-driven-development` | Влияние на HLD/LLD/API/Data/Events; ADR значимых решений | Определены контракты, NFR и затронутые документы |
| Планирование | `planning-and-task-breakdown` | План и единственный источник исполняемых задач | Зависимости, критерии и проверки есть; чужой незавершённый план сохранён |
| Реализация | `incremental-implementation`, `test-driven-development`, `source-driven-development` | Код и затронутая документация изменяются вместе | Вертикальный срез подтверждён проверками |
| Проверка | `debugging-and-error-recovery`, применимые специализированные skills | Доказательства приёмки, совместимости, актуальности документов | Обязательные проверки пройдены; ограничения явно перечислены |
| Review | `code-review-and-quality`, `documentation-and-adrs` | Сверка SPEC → код → HLD/LLD/ADR; фиксация подтверждённого долга | Нет необъяснённых расхождений; изменения документации проверены |
| Выпуск | `git-workflow-and-versioning`, `ci-cd-and-automation`, `shipping-and-launch`, `observability-and-instrumentation` | CHANGELOG, эксплуатация, rollback; целевое состояние сверяется с фактическим | Выполнены правила платформы и продукта, приложены доказательства |
| Развитие | `deprecation-and-migration`, `performance-optimization`, `code-simplification` | Долг → задача или инициатива → SPEC → план | Эффект проверен; закрытие долга имеет доказательство |

Skills по UI, браузеру, доступности и безопасности выбираются по области изменения; полный набор перечислен в [карте upstream](upstream.md). Оценка влияния и результаты проверки записываются в разделах существующего плана или задачи. Отдельные документы для них не создаются. Эксплуатация и безопасность описываются в HLD/LLD, а проверяемые требования — в SPEC и задачах.

До изменения: определить затронутые документы и обозначить целевое состояние. После: обновить фактическое состояние и приложить проверку. Если влияние отсутствует, кратко объяснить почему. Не менять несвязанные LLD при локальной правке.

Полный цикл SPEC и согласований применяется в случаях, заданных upstream. Сам профиль не отменяет gates навыка. Для исправления опечатки или иной самодостаточной малой правки применяются исключения upstream, а не создаётся формальная SPEC задним числом.

Не перезаписывать незавершённый `tasks/plan.md` другой работы. Сначала согласовать разрешение конфликта. Завершённые планы можно архивировать в `tasks/archive/<change>/` с сохранением ID и обновлением ссылок. Параллельные планы требуют явно выбранных путей и проверки адаптеров; по умолчанию активный план один.

Внешний трекер — единственный источник статусов, назначений и зависимостей исполняемых задач, когда он выбран. План содержит упорядоченные ссылки без зеркального списка статусов. Markdown-описания задач составляются на русском с YAML frontmatter в теле, если трекер сохраняет его; системные поля трекера не дублируются как авторитетные метаданные. Если трекер удаляет frontmatter, платформенный адаптер обязан определить проверяемое отображение или выбрать локальный режим. Нельзя молча считать такую интеграцию совместимой.
