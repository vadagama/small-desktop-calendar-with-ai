# План реализации Small Desktop Calendar

Дата: 28 октября 2026 года. Статус: **T01–T03 проверены, контрольная точка A пройдена**.
Задачи ведутся локально в [todo.md](todo.md), не в Linear.
Каждый этап завершается отдельным PR и открытием приложения для проверки
пользователем. Для T01, у которого ещё нет окна, проверяется исполняемое ядро.
Результаты первого среза — в [отчёте T01](../docs/implementation/t01-sdk-runtime.md).
Результаты desktop-срезов — в [отчёте T02–T03](../docs/implementation/t02-t03-desktop.md).
Решение по ADR-002 принято; остальные условия начала следующих срезов сохраняются.

## Принятые решения и предположения

- [Цели discovery](../docs/discovery.md) подтверждены; подробные требования
  и оставшиеся вопросы — в [спецификации](../docs/spec-v1.md).
- [ADR-003](../docs/decisions/003-agent-harness.md): Vercel AI SDK (Core + UI)
  выбран пользователем. eve и Pi не являются обязательными прототипами.
- [ADR-002](../docs/decisions/002-desktop-stack.md): Electron + React + Dockview
  приняты пользователем. Интеграции macOS и запуск упаковки проверяются
  отдельно от выбора стека.
- Первый SDK-срез можно проверить независимо от оболочки на синтетической
  модели и безопасных инструментах, без Small-токена и реальных встреч.
- Разработка идёт по вертикальным сценариям; каждый срез должен иметь
  собственную проверку результата, а не только список созданных файлов.

## Первый срез: T01

Результат — минимальное TypeScript-ядро на выбранном Vercel AI SDK,
воспроизводимо выполняющее безопасный синтетический tool. Этот срез не создаёт
готовое приложение и не доказывает совместимость с Small vLLM.

1. Проверить актуальные package metadata, зависимости и Node engine;
   зафиксировать версии `ai` и OpenAI-compatible provider в манифесте/lockfile.
2. Реализовать один tool с входной схемой и контролируемым результатом,
   поток событий и отмену. Имена/данные — синтетические, без календарных payload.
3. Использовать модель-заглушку на границе LLM, но реальный SDK-loop;
   проверить успешный вызов, некорректные аргументы и прерывание.
4. Записать реальные команды проверки в README среза после создания манифеста.

Для этого среза не требуются ключи, новый сервер, Keychain-записи или внешний
LLM-вызов. UI-протокол проверяется позже в T03 через фактический transport.

## Принципы реализации

- Привилегии и ключи остаются в доверенном процессе. Renderer и модель
  получают только нужные операции; нет произвольного shell или raw IPC.
- Вызов модели не является подтверждением записи. Контроллер связывает
  согласие пользователя с аккаунтом и версией карточки; изменение её отменяет.
- Состояние подтверждённой операции сохраняется до запроса. После неизвестного
  исхода сначала сверяется сервер, затем принимается решение о повторе.
- Арифметика слотов и аналитики проверяется кодом; модель формулирует запросы
  и пояснения. Названия тем/команд без доказательств не превращаются в факты.
- Часовой пояс явно передаётся на границах. Серии, исключения и перенесённые
  вхождения имеют устойчивую идентичность после проверки серверного контракта.
- Пример Vercel Chatbot используется как справочник UI, а не основание
  автоматически добавлять Next.js, Neon, Blob, Gateway или облачный вход.

## Проверки и ограничения

В корне есть манифест T01: `npm test`, `npm run typecheck`, `npm run build`
и `npm run format:check`. Он проверяет отдельное SDK-ядро. У UI-стенда
в `prototype/` свой манифест; его команды выполняются из этой директории.
Desktop-сборка ещё не настроена. Далее каждый срез использует команды своего
фактического манифеста.

Проверки делятся на:

- автоматические: синтетические данные, предсказуемая модель на границе,
  реальная прикладная логика, отсутствие отправки изменений до подтверждения;
- интеграционные: реальные read-only API и LLM только после безопасной настройки
  endpoint и ключей; секреты не запрашиваются через чат и не печатаются;
- desktop: упакованная arm64-сборка на текущем Mac, разрешения Keychain,
  Центр уведомлений, закрытие окна и пробуждение;
- записи: тестовое окружение или отдельно разрешённая конкретная операция.
  Работа над клиентом сама по себе не разрешает тестовые приглашения сотрудникам.

Runtime-результаты не заменяются успешными unit-тестами. При отсутствии доступа
к Small endpoint тест остаётся непроверенным, а синтетический результат
помечается отдельно. Числовые SLA задержки не вводятся.

## Риски и условия начала соответствующего среза

| Риск | Последствие | Проверка / решение |
| --- | --- | --- |
| Интеграции desktop-стека ещё не проверены | Выбор библиотеки не подтверждает Keychain и уведомления | Запуск и упаковка в T02; остальные проверки в своих срезах. |
| Неизвестны Small vLLM URL и model ID | Нельзя подтвердить реальный tool calling | Настроить профиль в T04; не использовать чужую модель как доказательство. |
| GitLab и часть API-схем недоступны | Неполные контракты | Подтверждать read-only ответами/исходниками, не угадывать. |
| Не подтверждён mapping person GUID → participant ID | Риск пригласить другого человека | T08 не выполняет подбор/запись с выдуманным ID. |
| Keychain binding и подпись | Запуск в dev не доказывает работу сборки | Проверка синтетического секрета и уведомления в упакованном приложении. |
| Неизвестный результат записи | Дубликат встречи | Журнал операции и сверка до повторного запроса. |
| Не утверждены правила аналитики и серий | Неоднозначный результат | Ревью соответствующих предложений перед T12/T13. |

Дистрибуция коллегам, обновления, другие версии macOS и архитектуры остаются
вне этого плана до отдельного решения. План не создаёт релизных обязательств.
