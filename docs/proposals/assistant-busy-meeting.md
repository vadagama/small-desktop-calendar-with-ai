# Встреча через AI при занятости участников

Статус: спецификация для согласования, реализация не начата.

## Цель и сценарий

Пользователь может сохранить выбранное время и полный состав встречи, даже
если участники заняты. AI готовит карточку, но создание выполняется только
после явного согласия пользователя в интерфейсе.

1. Проверить занятость выбранного состава, включая организатора.
2. При пересечениях показать карточку с исходным временем и составом,
   предупреждение «В это время есть занятые участники» и имена занятых людей.
   Не раскрывать названия и содержание их встреч.
3. Показать выключенный по умолчанию флажок
   «Согласен создать встречу, несмотря на занятость участников».
4. До установки флажка кнопка «Создать встречу» недоступна. Нажатие кнопки
   после установки флажка подтверждает создание конкретной версии карточки.
5. Перед записью повторно проверить занятость. Если состав конфликтов изменился,
   показать актуальное предупреждение и запросить согласие заново.

Просьба в чате «игнорируй занятость» разрешает подготовить такую карточку,
но не заменяет подтверждение в интерфейсе. AI не получает инструмент записи.
Обычная встреча в свободное время сохраняет текущий сценарий подтверждения.

## Границы

- Согласие привязано к аккаунту, ID и версии зарегистрированного черновика,
  времени, составу и показанным конфликтам. Редактирование снимает согласие.
- Main проверяет наличие согласия независимо от состояния кнопки в renderer.
  Модель не может передать собственное подтверждение через аргументы инструмента.
- Ошибка API, неполная занятость, неизвестный формат ответа или недоступность
  данных не считаются доказательством конфликта и не разрешают обход проверки.
- Разрешается пересечение встреч участников, включая организатора. Это согласие
  не отменяет ограничения переговорных, права доступа и прочие проверки.
  Перерыв организатора и сохранённые временные предпочтения не отключаются
  автоматически; используются существующие правила разовых исключений.
- Сохраняются защита от дублей, привязка к сессии, проверка ответа после записи
  и запрет повторного POST при неизвестном результате.
- Первый срез — разовая встреча через AI. Ручная форма, серии и изменение
  существующей встречи находятся вне этого изменения.
- Настройки, профили и пользовательские данные не меняются. Новых зависимостей
  и реальных встреч для проверки не требуется.

## Текущее устройство и контракт

Electron + React + TypeScript + Zod; версии закреплены в `package.json`.

- `src/main/meeting-draft.ts` отклоняет интервал без общего свободного слота.
- `src/main/meeting-writer.ts` повторяет проверку перед записью.
- `src/renderer/MeetingDraftCard.tsx` показывает карточку и кнопку создания.
- `src/main/meeting-operations.ts` управляет версиями и журналом операций.
- `src/shared/meeting-draft.ts` и `src/shared/meeting-operations.ts` задают контракт.
- `src/agent/calendar-runtime.ts` и контент агента описывают доступные действия.

Текущий путь записи в `src/main/meeting-request.ts` содержит `force=false`.
До изменения отправки необходимо проверить контракт backend/public frontend:
поддерживается ли создание с занятостью участников, что именно отменяет `force`,
какие права нужны и как сервер сообщает конфликты. Имя параметра не является
доказательством его семантики. Не расширять разрешённые запросы до произвольных
URL или тел. Если контракт недоступен, явно зафиксировать ограничение проверки.

Новые поля валидировать строгими Zod-схемами по существующему стилю:

```ts
z.strictObject({
  id: z.uuid(),
  revision: z.number().int().positive(),
});
```

UI использует существующие компоненты, компактную плотность и токены
`--font-*` согласно `docs/design/typography.md`. Флажок имеет видимую подпись,
управляется клавиатурой, предупреждение доступно средствам чтения экрана.

## Проверка и критерии приёмки

Unit-тесты в `tests/agent/`: подготовка конфликтного черновика, отсутствие
согласия, старая версия, чужой аккаунт, изменение конфликтов, ошибка получения
занятости, свободное время, защита от дублей и неизвестный результат записи.

Electron E2E в `tests/desktop/`: запрос AI → карточка с полным составом и
предупреждением → недоступная кнопка без согласия → флажок → одна отправка →
проверенное событие. Дополнительно: снятие согласия после редактирования,
обновление конфликтов, управление клавиатурой и computed font-size.
Использовать синтетический API, изолированный профиль и скрытые окна Electron.

Команды из актуального `package.json`:

```sh
npm test
npm run typecheck
npm run build:desktop
npm run test:desktop -- tests/desktop/assistant.spec.ts
```

Точный целевой E2E-файл выбрать при реализации по расположению существующих
сценариев; новые тесты обязаны сначала воспроизвести текущую блокировку.
Проверить форматирование затронутых файлов через локальный Prettier.
Обновить документацию создания встреч, которая сейчас описывает запрет обхода.

## Вопросы

Продуктовых вопросов нет: предлагается отдельный флажок в карточке.
Семантика серверного режима создания с пересечениями требует исследования
контракта на этапе реализации; реальные приглашения не отправлять.
