# Быстрый календарь и ассистент с локальным индексом

Начать после [миграции на Go и Wails](INIT-0001-wails-migration.md). Цель — ускорить открытие недели, поиск людей и подбор времени, сохранив точность при изменениях со стороны коллег. Первый этап — проверить контракт Small и измерить мигрировавший клиент. SQLite и локальная модель остаются кандидатами до замеров.

## Сценарии и данные

| Действие | Предлагаемое поведение |
| --- | --- |
| Открыть неделю | Показать сохранённые встречи, обновить видимый диапазон в фоне. Перенос, отмена и новый состав отражаются также в открытой карточке. Офлайн показать время последней успешной проверки. |
| Набрать фамилию | Искать по разрешённым полям справочника, среди совпадений поднимать недавних и частых коллег. При совпадении имён предложить выбор. При промахе обратиться к Small. Полный справочник загружать только при наличии соответствующего API и прав. |
| Спросить «Когда следующая встреча с Анной?» | Найти сотрудницу по ID, проверить диапазон и открыть найденное событие из ответа. Перенос может изменить порядок встреч. Для вопроса о составе конкретной встречи достаточно проверить её карточку. |
| Найти встречи по теме за месяц | Использовать локальный текстовый индекс названий. Перед выводом об отсутствии результатов догрузить непокрытые даты. Оценить FTS5 на реальных формах запросов с синтетическими данными. |
| Подобрать окно группе | Предварительно читать занятость частых коллег на ближайшие рабочие дни. Изменение длительности с 60 до 30 минут или исключение участника сразу пересчитывает окна по уже полученным интервалам. |

## Хранение и обновление

Общий сервис чтения в Go обслуживает UI и инструменты ассистента. Каждая выдача содержит данные, подтверждённый диапазон и время проверки. В SQLite хранить собственные экземпляры событий, связи с участниками, разрешённые поля людей и интервалы занятости. Индексы подобрать для запросов по участнику и времени. Отдельно учитывать полноту по человеку и дню. Пустая подтверждённая занятость позволяет искать окна, пропущенный ответ означает неизвестность. Сохранить правила рабочих часов, часовых поясов, буферов и повторений. [Правила подбора времени](../implementation/availability-source.md).

Одна фоновая очередь отдаёт приоритет открытому диапазону, затем ближайшему месяцу собственных встреч и занятости частых коллег. Объединять одинаковые запросы от чата и UI, использовать групповое чтение занятости за день, обновлять после записи, возврата в окно и пробуждения. Ограничить фоновые запросы при ошибках и офлайн. Операции с диском и индексацию выполнять вне потока UI. Изолировать данные по аккаунту, шифровать также поисковый индекс и служебные файлы БД, очищать кэш при выходе и учитывать отзыв доступа. Новый профиль начинает с пустой базы.

## Как проверить свежесть

Исходный ориентир Electron — опрос открытого диапазона раз в 60 секунд и сравнение содержимого, встречи ассистент читает из сети. После миграции повторно снять базовые показатели. [Описание синхронизации](../implementation/offline-first-calendar-sync.md).

Сохранять серверный updated_at вместе с той версией встречи, которую он описывает. Сравнивать его на равенство со следующим серверным значением. Локальный fetchedAt определяет возраст снимка. Проверить точность метки и обновление связанных данных. Для недели проверить ETag выборки для того же аккаунта, диапазона и фильтров. При поддержке If-None-Match сервер может подтвердить снимок ответом 304 или вернуть обновлённую выборку. Проверка известных ID сама по себе пропускает новые встречи. Резервный путь — полное чтение диапазона и сравнение содержимого. Серверные уведомления при наличии могут инициировать такое обновление.

Точный ответ ассистента подтверждать чтением соответствующего события или диапазона. Для выбранного окна перепроверять фактический состав и время. Защита от правки между чтением и сохранением требует атомарной проверки серверной версии при записи. При конфликте показать изменения для повторного решения. Гарантия свободного слота при создании требует проверки конфликта в той же серверной операции. Поддержку обеих гарантий исследовать отдельно.

## Контрактный эксперимент после миграции

В согласованном тестовом календаре аккаунт A меняет синтетическую встречу, B читает через API приложения. Для удаления участника проверить также его собственную видимость. Снимать исходный снимок и после каждого подтверждённого действия сравнивать стратегию с полным чтением без локального кэша и условных заголовков. Сверять карточку и список, идентификаторы экземпляров, время, состав и принадлежность диапазону. Удалять созданные тестом данные. В отчёт включать обезличенные результаты, без токенов и тел реальных встреч.

| Проверка | Наблюдение |
| --- | --- |
| Повтор без изменений | Стабильность updated_at и ETag, фактическая реакция на If-None-Match. |
| Добавить и убрать участника без других правок | Изменились ли метка карточки, версия недели, видимый состав и доступ исключённого аккаунта. |
| Дважды быстро перенести встречу | После каждой записи прочитать состояние. Проверить, различимы ли два сохранения в пределах точности метки. |
| Перенести встречу через границу недель | Проверить исчезновение из старой и появление в новой неделе, включая обе версии выборок. |
| Создать и отменить встречу | Проверить изменение состава выборки при появлении и исчезновении ID. |
| Перенести отдельный экземпляр серии | Сравнить изменённый экземпляр, соседний экземпляр и версию диапазона. |

Начать с повтора без правок, смены состава и переноса между неделями. Если полное чтение уже видит изменение, а стратегия считает кэш свежим, зафиксировать контрпример и исключить её как единственный способ проверки. Задержку появления изменений в самом полном чтении измерять отдельно. Отсутствие контрпримеров описывать в пределах проверенных случаев.

## Этапы и критерии выбора

1. На одинаковых сценариях сравнить полное чтение с диффом, проверку меток и условный запрос диапазона. Для изменившейся и неизменившейся недели измерить запросы, байты и время до первого отображения и до подтверждения. Учитывать повторную загрузку после проверки метки.
2. Проверить SQLite на справочнике, собственной неделе и командах «что завтра» и «когда встреча с…». Сравнить холодный и прогретый старт с файловым кэшем на одном устройстве. Проверить офлайн, смену аккаунта и неполное покрытие.
3. Проверить повторное использование занятости при подборе. Включать предварительную загрузку частых коллег по измеренной доле попаданий и числу запросов к Small за рабочий день.
4. Простые намерения обрабатывать локально правилами. Отдельным экспериментом проверить малую модель для разбора свободной фразы в группу, длительность и диапазон. Эмбеддинги оценивать для смыслового поиска встреч. Сравнить точность русских запросов, холодный старт, память, размер пакета и задержку полного ответа.

Решение о внедрении принять по результатам контрактных тестов и воспроизводимому выигрышу для пользователя относительно мигрировавшего клиента. Ожидаемый результат исследования — таблица наблюдений, выбранная стратегия по каждому сценарию и явно описанные пределы свежести.
