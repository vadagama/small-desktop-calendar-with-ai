# План: локальный кэш календаря и фоновая синхронизация (read-offline-first)

Статус: ЧЕРНОВИК v2 (учтены ответы пользователя, см. раздел «Решения пользователя»), ждёт одобрения. Код не менять до одобрения.
Область: чтение событий — кэш + stale-while-revalidate + фоновый опрос + анимация изменений.
Вне области: офлайн-очередь записи (остаётся online-only через существующий `EventMutationJournal`).
Метод: скилл `make-plan` (Phase 0 → фазы → финальная верификация), анимации по скиллу `vercel-react-view-transitions`.

## Phase 2. Чистые функции: нормализация и диф

**Статус: выполнено 29.10.2026** (`src/shared/calendar-diff.ts`, `tests/agent/calendar-diff.test.ts`). Отклонение от плана: отпечаток — каноническая JSON-строка, а не SHA-256, чтобы функция работала и в renderer (без `node:crypto`); хэшировать при необходимости будет кэш (Phase 3). `moved` и `changed` не пересекаются; перенос вхождения серии даёт `removed`+`added`, потому что ключ серии содержит время начала.


Что реализовать (новый файл в `src/shared/`, напр. `calendar-diff.ts`; стиль — как `calendar-time.ts`):

- `diffEvents(prev, next): { added: string[]; removed: string[]; changed: string[]; moved: string[] }` — по `event.key`.
- Тип `CalendarSnapshot = { events; issues; fetchedAt; complete: boolean }`.

Ссылки: паттерн `fingerprint`/`mutationHash` в `event-reschedule.ts`, `event-mutation-journal.ts`.

## Phase 3. Хранилище кэша в main

**Статус: выполнено 29.10.2026** (`src/main/event-cache.ts`, `src/main/event-cache-cipher.ts`, `tests/agent/event-cache.test.ts`, 14 тестов). Отклонения и решения:
- Шифр внедряется интерфейсом `CacheCipher`; адаптер `safeStorageCipher` (async-методы Electron 45) лежит отдельно и **ещё нигде не подключён** — подключение в `index.ts` и очистка кэша при выходе/смене аккаунта относятся к Phase 4.
- Раскладка: `<dir>/<sha256(account)[:32]>/<sha256(kind+key)>.json`, внутри только шифртекст; в payload дублируются `accountId`, `key`, `kind`, при несовпадении файл — промах и удаляется.
- `shouldReEncrypt: true` трактуется как промах (кэш одноразовый, перечитаем из Small) — не полагаемся на двусмысленную фразу документации про повторный вызов.
- Без шифра — только память (файлы не создаются). TTL: события 7 сут, справочники 24 ч. LRU 40 записей на аккаунт по mtime (с внедряемыми часами). Лимит значения 4 МБ.
- `putEvents` отказывает при любых `issues` и при несоответствии схеме. Ключ диапазона `eventRangeKey` строится по реальному диапазону (`calendarRange`), а не по дате.
- `ParticipantMemory` для справочников не переиспользован: он хранит пользовательские алиасы, а не результаты поиска.
- Риск: на macOS первое обращение к `safeStorage` может вызвать запрос Keychain («… Safe Storage»); проверить в dev-сборке в Phase 4.
- Не сделано: запись на диск — best-effort, ошибки записи глотаются; чтение из памяти не обновляет mtime (запись, которую читают только из памяти, может быть вытеснена с диска раньше).


Что реализовать (`src/main/event-cache.ts`, по образцу `EventMutationJournal`):
- Каталог `userData/event-cache/`, `0700`; файлы `0600`; temp+rename+fsync; имя файла — `sha256([accountId, rangeKey])`.
- Содержимое шифруется `safeStorage.encryptStringAsync`; при недоступности (`isAsyncEncryptionAvailable() === false`) — **кэш на диск не пишется**, только память (п.3: хранение на диске разрешено; запасной вариант — память).
- Метаданные: `fetchedAt`, `schemaVersion`, `complete` (не кэшировать ответы с issues «Полнота не подтверждена» как полные).
- `get/put/clear(accountId)`; очистка при выходе и смене аккаунта; TTL; повреждение файла → игнорировать кэш, а не блокировать работу (в отличие от журнала мутаций).
- Окно (п.4): недельный диапазон текущего вида плюс соседние недели (предзагрузка ±1 неделя); LRU по диапазонам.
- Отдельный долгоживущий кэш для редко меняющегося: список календарей (`calendars`) и результаты поиска сотрудников (`searchPeople`), TTL по умолчанию 24 ч (**допущение, подтвердить**). Перед реализацией прочитать `ParticipantMemory` (`userData/participant-memory/`), чтобы не дублировать: возможно, переиспользовать.

Верификация: `tests/agent/event-cache.test.ts` — изоляция аккаунтов, права 0700/0600, повреждённый файл, TTL, `shouldReEncrypt`, очистка при logout.
Guard: не логировать содержимое; не хранить сессию/куки в кэше.

## Phase 4. Сервис синхронизации и IPC

**Статус: выполнено 29.10.2026** (`src/main/calendar-sync.ts`, `tests/agent/calendar-sync.test.ts` — 16 тестов; правки `calendar.ts`, `calendar-ipc.ts`, `small-auth-ipc.ts`, `index.ts`, `preload/index.ts`, `shared/calendar.ts`). Решения и отклонения:
- **Обратная совместимость:** `calendar:events` отдаёт кэш только при `allowStale: true`; без флага — сеть, как раньше. Renderer не менялся, флаг включит Phase 5.
- Любая подтверждённая загрузка (в том числе обычное чтение) пишет кэш и рассылает push `calendar:changed` (`events` с `diff`, либо `status`: `online | offline | auth-expired`). Это единый путь для опроса и ручного обновления; renderer пока не подписан.
- Опрос 60 с только диапазона, который смотрит пользователь; пропуск при скрытом окне и при `net.isOnline() === false`; backoff ×2 до 10 мин; догон при фокусе окна (`wake`); 401 останавливает опрос до следующего успешного чтения; один запрос на ключ диапазона одновременно.
- Сброс (`reset`: кэш, таймер, диапазон) при входе и выходе; инвалидация (`invalidate`: кэш) после любой попытки записи — `respond`, `reschedule`, `applyChange` и создание встречи (`MeetingWriter.create`, обёрнут в `index.ts`). Поздние ответы после сброса/инвалидации не попадают в кэш и в push (счётчик поколений).
- Ассистент по-прежнему читает через `CalendarService` напрямую; кэш к нему не подключён (п.7).
- Неполные ответы (`issues`) отдаются вызывающему, но не кэшируются и не порождают «удалённых» событий в diff.
- **Не сделано:** предзагрузка соседних недель (±1) — отложена на после Phase 5; кэш справочников (календари, поиск людей) — Phase 8; точечная инвалидация вместо полной очистки — Phase 7.
- **Не проверено:** реальная работа `safeStorage` на диске в Electron (desktop-сценарии проходят, но шифрование там не проверялось отдельно); запрос Keychain «Small Calendar Safe Storage» при первом запуске; push не принимается renderer'ом.
- **Известный сторонний сбой:** `tests/desktop/calendar-assistant.spec.ts` падает на сохранении профиля модели («Профиль сохранён») и воспроизводится на копии без изменений Phase 4; связанные файлы (`ModelSettings.tsx`, `profiles.ts`, `keychain.ts`, `shared/profiles.ts`) имеют ваши незакоммиченные правки.

Что реализовать (`src/main/calendar-sync.ts`, поверх неизменного `CalendarService.events`):
- `CalendarSync.read(query)`: сразу отдаёт кэш (`stale: true`, `fetchedAt`), параллельно ревалидирует через сеть; при успехе обновляет кэш и, если диф непустой, шлёт push `calendar:changed` с `{ key, snapshot, diff }`.
- Фоновый опрос: только для активного аккаунта и видимого диапазона; только при `BrowserWindow` focused/visible; интервал 60 с (п.1); экспоненциальный backoff при ошибках; `net.isOnline() === false` → не опрашивать.
- Статусы: `fresh | stale | offline | auth-expired`; `401` → существующий путь `expired()` (`SmallAuth`), без повторных попыток.
- Защита от гонок: `requestId`/`SmallAuth.version`, один in-flight запрос на ключ диапазона, отмена при смене аккаунта.
- Новые IPC: ответ `calendar:events` расширяется (`snapshot` + `freshness`), добавляется push-канал `calendar:changed` в `calendarChannels` (`src/shared/calendar.ts:49-61`), `ipcRenderer.on` в `src/preload/index.ts` по образцу стрима ассистента (`:22-26`), в `CalendarBridge` (`shared/calendar.ts:86-120`) — подписка с отпиской.
- Потребители ассистента (`schedule.ts`, `meeting-writer.ts`) остаются на `CalendarService.events` напрямую (сеть, без кэша) — решение зафиксировано в Phase 8.

Верификация: unit-тесты на фейковых `CalendarService` и таймерах (node:test): stale→fresh, ошибка сети не стирает кэш, backoff, смена аккаунта отменяет, 401 → auth-expired, один in-flight. Новые GET-пути не добавляются (используются прежние) → `isCalendarReadPath` не меняется.
Guard: никакого опроса из renderer; не добавлять событие на `net`/`app`.

## Phase 5. Хук renderer

**Статус: выполнено 29.10.2026** (`src/renderer/useSmallCalendar.ts`, чистая логика в `src/shared/calendar-view-state.ts`, `tests/agent/calendar-view-state.test.ts` — 13 тестов, сквозной `tests/desktop/calendar-sync.spec.ts`). Решения и отклонения:
- Состояние — `CalendarStore`: до 8 недавно просмотренных диапазонов (LRU). Возврат к просмотренному диапазону показывает события сразу, без экрана загрузки. Ключ данных не содержит `reload`, поэтому ручное обновление не стирает события. Данные другого аккаунта или диапазона не показываются никогда.
- Навигация и первая загрузка идут с `allowStale: true`; `refresh()` и перезагрузка после записи — всегда в сеть (`allowStale: false`) и оставляют в хранилище только обновляемый диапазон (остальные могли устареть из-за записи).
- Подписка на `calendar:changed` (в `startTransition`): `events` применяется к своему диапазону, более старый ответ игнорируется, повтор того же ответа безвреден; `status`: `offline`/`online`, `auth-expired` вызывает `expired()`.
- Ошибки: без данных — блокирующая `error` (как раньше); с данными — неблокирующая `refreshError` и заметка «Показаны данные на HH:MM» (`.calendar-notice`, `role="status"`; класс `.calendar-warning` занят существующими тестами). При `offline` та же заметка.
- Хук отдаёт для Phase 6: `changes: { diff, revision }` (последний непустой диф диапазона; `revision` растёт только при изменении), `stale`, `offline`, `refreshing`, `fetchedAt`.
- Для теста добавлена переменная `SMALL_TEST_SYNC_INTERVAL_MS` (только в неупакованной сборке; упакованное приложение всегда 60 с).
- Сквозной тест подтверждён мутациями (отключение push, хранилище на 1 диапазон, ключ с `reload` — каждая роняет его) и 3 прогонами подряд.

## Риски

| Риск | Смягчение |
|---|---|
| API не отдаёт версию → диф только по отпечатку, лишние обновления | Phase 1, нормализация в Phase 2 |
| Хранение содержимого встреч на диске | шифрование `safeStorage`, 0600, TTL, очистка при logout; опция «только память» |
| Устаревшие данные приводят к неверным слотам ассистента | ассистент читает из сети; метка возраста |
| Конфликт VT с абсолютным позиционированием и драгом | VT опционален, отключается во время жеста; fallback на CSS |
| Нагрузка/блокировка аккаунта частым опросом | focus-only, backoff, один in-flight, лимит окна |
| Изменение DOM ломает 10+ Playwright-спецификаций | не менять селекторы/aria; атрибут `data-change` аддитивный |
