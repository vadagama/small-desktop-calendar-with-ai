# T13 — Явная область операции серии

Реализовано 29 октября 2026 года. **Клиентская часть готова, серверный контракт
серий не подтверждён, запись серий закрыта.** Тестовой среды Small нет:
[протокол проверки](../research/series-contract-probe.md) и скрипт подготовлены,
но на реальном сервере не запускались. Узнавание вхождения в разных видах
(срез 6) реализовано отдельным PR: [алиасы вхождения](t13-occurrence-aliases.md).

## Что видит пользователь

Для повторяющейся встречи (организатор, сегодня или позже) меню карточки
открывает диалог области вместо прямого действия: «Редактировать»,
«Перенести» (только для серий) и «Удалить».

- Область: «Только это вхождение» (по умолчанию) и «Это и последующие». Для
  удаления вторая область недоступна: «для удаления доступно только одно вхождение».
- Над областью показаны название и время вхождения, под ней текст подтверждения:
  область, дата и что остаётся нетронутым («Прошедшие встречи не изменятся»).
- Пока контракт не подтверждён, кнопка записи неактивна, а причина написана в
  диалоге: «Переименование (это и последующие) пока недоступно: поведение
  повторяющихся встреч в Small ещё не подтверждено проверкой на тестовой среде.
  Обычные встречи работают как раньше».
- Прошедшие вхождения не предлагают ни одного действия.
- Обычные (неповторяющиеся) встречи идут прежним прямым путём T10, диалог не открывается.
- Перенос жестом (перетаскивание и растягивание) по-прежнему только для разовых встреч.

### Политика (`decideSeriesOperation`)

- Операции: переименование, перенос, удаление. Области: `occurrence`, `following`.
  «Удалить последующие», вся серия, значения `all` и `future` не поддерживаются.
- Прошедшее определяется календарным днём Asia/Almaty (не UTC): вхождение, у
  которого прошла исходная дата или текущий день, не меняется; перенос на
  прошедший день запрещён. Вхождение с исходной датой в прошлом, перенесённое в
  будущее, тоже считается прошедшим (консервативное решение).
- Для каждой комбинации политика сообщает, нужна ли материализация и какие
  допущения контракта (A2–A9) должны быть подтверждены.
- Ключ вхождения `series:{id}:{исходная дата}` не меняется при переносе;
  прежний ключ `series:{id}:{мс}` оставлен как `legacyOccurrenceKey`.

### Гейт контракта

`seriesContractEvidence` пуст, поэтому все новые операции серий закрыты.
`gateSeriesOperation` сначала применяет политику (причины `past`,
`move-to-past`, `unsupported-scope`), затем сверяет нужные допущения с
подтверждёнными (`contract-unverified`). Открытый гейт выдаёт замороженный
`SeriesApproval`; адаптер принимает только такие объекты (копия не проходит) и
только для той операции и области, для которых одобрение выдано.

Чтобы включить операцию: прогнать протокол на разрешённой среде, записать
результат в `docs/research/series-contract-results.md` строками «A<n>: подтверждено»,
добавить допущения в `seriesContractEvidence` (тест не принимает запись без этого
документа) и отдельно расширить список разрешённых путей транспорта.

Уже работающий перенос собственного вхождения серии с `single` (T10) через гейт
не идёт и работает как раньше.

### Адаптер и журнал

Порядок: сверка прежней записи журнала, чтение окна, проверка актуальности
интервала, организатора и полноты карточки, заявка в журнале с `fsync`,
материализация (если вхождение виртуальное), запись, подтверждение ответа,
сверка чтением, очистка журнала.

- Неполная карточка не превращается в пустые списки: запись блокируется.
- Блокировка идёт на всю серию. После таймаута, ошибки 5xx, неподтверждённого
  результата или перезапуска следующая попытка только читает; позднюю запись
  распознаёт и новый экземпляр сервиса. Новое действие не обходит блокировку.
- Явные отказы (400/401/403/404/409/422) освобождают журнал.
- Запрос, который не ушёл из приложения (локальный отказ транспорта), освобождает
  журнал сразу: повтор безопасен.
- Потерянный ответ отмены не доказывает успех, даже если вхождение исчезло:
  нужен подтверждённый ответ, как для удаления в T10.
- Успех подтверждается чтением окна вокруг вхождения (с −14 до +84 дней от
  исходной даты): изменено нужное, остальное, включая прошлые вхождения в окне,
  не тронуто. Вхождения вне окна не проверяются.
- В журнале только хеши, даты окна и состояние; названий и участников нет.
- Журнал серий лежит в `userData/series-mutations/`; при закрытом гейте каталог
  не создаётся.

### Защита в глубину

Список разрешённых путей транспорта (`small-session.ts`) намеренно **не
расширен**: `from-template`, `cancel` и `PUT` с `all-next` он отклоняет. Если гейт
по ошибке открыть, запись упрётся в транспорт, вернётся «запрос не отправлен»,
журнал освободится. Проверено разовым экспериментом: гейт временно открыт,
приложение запущено с серией из синтетического API, на сервер ушло 0 запросов,
каталог журнала пуст. Эксперимент откатан; постоянным тестом он быть не может,
потому что подтверждения нельзя подставить в собранное приложение.

## Допущения о сервере (не подтверждены)

Все допущения A1–A10 из протокола остаются непроверенными: идемпотентная
материализация (A2), `single` меняет одно вхождение (A3), стабильный ключ
перенесённого вхождения (A4), семантика `all-next` (A5), включительность `UNTIL`
(A6), отмена вхождения (A7), локальная дата в Asia/Almaty (A8), права
не организатора (A9), отсутствие ETag (A10). Тесты адаптера идут на синтетическом
backend, где эти допущения заложены явно (и помечены в тесте). Они фиксируют
поведение кода, а не сервера.

Имена полей тела `from-template` (`original_event_id`, `date`) и `cancel`
(`reason`) взяты из клиентского bundle и не подтверждены.

  бэкенд 7, методы записи сессии 1). Всего в наборе 266.
- Электрон: `series-gate.spec.ts` (мост, закрытый гейт, отказ записи, ноль запросов

- Проверка чувствительности (код менялся, тест должен упасть): защиты скрипта
  пробы (6 вариантов), политика области (8), гейт (7), адаптер (порядок «заявка
  до записи», сверка, повтор, одобрение, актуальность интервала, организатор,
  окно, блокировка серии, обработка 5xx и «не отправлено», неполная карточка),
  контроллер, бэкенд и признак «не отправлено» (10), интерфейс (9, включая всплытие `cancel` и цикл запросов
  к гейту). Все изменения ловятся. Несколько вариантов сначала выживали, и для них
  добавлены тесты.
- `npm run typecheck`, `npm test`, `npm run build:desktop`, `npm run test:desktop`,
  форматирование и `git diff --check`.

## Что поймали при разработке

- Escape во вложенном диалоге закрывал и карточку: React-событие `cancel`
  всплывало к обработчику карточки. Теперь всплытие останавливается.
- Диалог в цикле заново спрашивал гейт, потому что `seriesTarget` возвращал
  новый объект на каждом рендере; теперь запрос идёт по стабильному ключу, а
  сценарий проверяет, что в покое DOM не меняется.
- Модуль с `electron` нельзя импортировать в unit-тестах: контроллер вынесен
  отдельно от регистрации IPC.

## Вне этого PR

- **Срез 6 — узнавание вхождения в разных видах** реализован отдельным PR
  ([алиасы](t13-occurrence-aliases.md)): напоминания без повторов, аналитика без
  дублей, окно серий через общий `collectEvents`.
- Реальный прогон протокола на разрешённой среде и последующее включение гейта.
- Диалог показывает в тексте подтверждения ISO-дату («с 2026-10-29»); человекочитаемая
  дата стоит выше в самом диалоге.

## Ограничения

- Ключ вхождения восстанавливается из локальной даты начала: для перенесённых
  вхождений он верен только при допущении A4.
- Окно проверки ограничено; прошлые вхождения старше 14 дней и последующие
  дальше 84 дней не проверяются.
- Если материализация прошла, а сама запись отклонена, в календаре остаётся лишнее
  материализованное вхождение (его вид для пользователя не меняется).
- Полный набор Electron нестабилен независимо от T13 (см. [T12](t12-analytics.md));
  в последних прогонах этой ветки отказов не было.
