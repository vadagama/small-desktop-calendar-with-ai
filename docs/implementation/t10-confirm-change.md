# T10 — Подтверждённое изменение и отмена разовой встречи

В карточке события предпросмотр теперь содержит явное действие «Применить
название» или «Подтвердить отмену встречи». После успешной сверки карточка
закрывается и календарь перечитывается. До подтверждения выполняются только GET.
Изменение серий, перенос времени и изменение состава в этот срез не входят.

## Контракт и границы

Основание маршрутов — сохранённый публичный клиент Small, описанный в
[t10-change-preview.md](t10-change-preview.md): изменение использует PUT
`/calendar/events/{id}?force=false`, отмена разовой встречи — DELETE того же
ресурса без force. Это удаление для всех участников; UI явно сообщает об этом.
POST cancel для вхождения серии и from-template не разрешены.

Предпросмотр сравнивает creator_id с GUID сотрудника (guidfl), а не с uid сессии.
Полный снимок для PUT включает описание, место, время, timezone, публичность,
календари, участников, информируемых и вложения. Пустые nullable-поля сохраняются.
Main хранит снимок в памяти; renderer получает только ID предложения и поля
предпросмотра. Подмена payload через подтверждение невозможна. Новый IPC проверяет
доверенное окно, активный аккаунт и ревизию сессии. Транспорт разрешает только
узкие PUT/DELETE-пути, валидирует тело и не делает refresh-and-replay записи.

Перед записью событие заново читается, проверяются организатор, разовый тип и
равенство снимка. Изменение любого сохраняемого поля блокирует старый предпросмотр.
Серверный compare-and-swap/ETag не подтверждён: остаётся окно гонки между последним
GET и PUT/DELETE, поэтому полной защиты от параллельных внешних правок не заявляем.
Семантика сохранения всех полей при реальном PUT пока проверена только на
синтетической границе; требуется разрешённое тестовое окружение Small.

## Исходы и журнал

До запроса атомарно сохраняется намерение. На диске находятся только хеши и
квитанции, без тела встречи и персональных payload. Последовательные операции
над событием получают поколения журнала; завершённые поколения допускают новое
намерение, незавершённое/неопределённое поколение нельзя обойти другим действием.
Восстановленный успех повторно сверяется, чтобы старое предложение из другого
окна не выдавало устаревший результат за актуальный.

Переименование подтверждается чтением полного ожидаемого снимка. Отмена требует
положительного ответа DELETE (204 либо JSON status=success) и последующего 404.
После потери ответа DELETE один 404 не доказывает отмену: результат остаётся
неопределённым, повторная запись запрещена. «Проверить результат изменения» только
читает. После перезапуска неизвестная операция продолжает блокировать новые
изменения; отдельный интерфейс восстановления предложений между запусками ещё
не реализован.

## Проверки

- 115 модульных тестов: запрет до подтверждения, чужой аккаунт/организатор, серия,
  устаревшие поля, смена сессии, однократная отправка, отсутствие refresh-replay,
  восстановление журнала, A→B→A→B, старое предложение из параллельного окна,
  потерянный ответ DELETE и успешная повторная сверка rename.
- 11 Electron-сценариев: отдельные сценарии переименования и отмены, сохранения
  данных, закрытия карточки, обновления календаря и отсутствия второго DELETE
  после потери ответа. Сервер синтетический, production заблокирован resolver-ом.
- typecheck, build:desktop и format:check проходят. Снимок подтверждения просмотрен.
- Инверсия проверки организатора ломает тесты; исходное условие восстановлено.
- Read-only предпросмотр двух реальных существующих событий прошёл. Диагностический
  транспорт запрещал все записи календаря. Реальные события не менялись.
- Независимое ревью выявило повторное использование старого успеха журнала;
  добавлены поколения и повторная сверка восстановленного успеха.

Этап выполнен в отдельном worktree, параллельные изменения оформления календаря
в основной рабочей папке не затронуты. Упакованная сборка не проверялась.
