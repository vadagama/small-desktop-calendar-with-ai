# Обновления календаря

Календарь использует `electron-updater` и публичные GitHub Releases репозитория
`vadagama/small-desktop-calendar-with-ai`. Канал — стабильные версии; черновики и
предварительные выпуски не устанавливаются автоматически.

## Поведение и критерии приёмки

- Проверка через 10 секунд после запуска и каждые 4 часа, независимо от входа
  в Small. Повторные запросы во время проверки или скачивания объединяются.
- Настройки модели → «Обновления»: текущая версия, проверка вручную, описание
  выпуска обычным текстом, прогресс, ошибки и повторная попытка.
- Доступная версия скачивается автоматически. Установка только после явного
  подтверждения перезапуска; «Позже» скрывает уведомление до следующего запуска.
  Обычный выход не устанавливает обновление.
- Перед перезапуском пользователь предупреждён о несохранённых изменениях.
- Обновлятор не меняет userData, настройки, авторизацию, ключи или контекст.
- IPC доступен только главному фрейму доверенного локального интерфейса.
  Адрес выпуска, токен GitHub и произвольные команды из renderer не принимаются.
- Локальные и dev-сборки показывают, почему автообновление недоступно.

## Реализация и проверка

Основная логика — `src/main/app-updates.ts`, Electron-интеграция —
`src/main/update-ipc.ts`, контракт — `src/shared/updates.ts`, интерфейс —
`src/renderer/AppUpdates.tsx`. Стиль: строгий TypeScript, именованные функции,
состояние через типизированный IPC, например `updates.check(): Promise<UpdateState>`.

Проверки: `npm test`, `npm run typecheck`, `npm run build:desktop`,
`npx playwright test -c playwright.desktop.config.ts tests/desktop/updates.spec.ts`.
Unit-тесты проверяют события, повторы, ошибки, расписание и запрет установки до
готовности. Electron E2E выполняются в фоне и проверяют настоящий IPC и интерфейс.

## Подготовка выпуска

1. `npm run package:mac:release`: нужны `SMALL_SIGN_IDENTITY` (Developer ID
   Application) и `SMALL_NOTARY_PROFILE`. Только этот режим вкладывает
   `app-update.yml` в Resources **до подписания**. Подпись и нотариализация
   проверяются существующим процессом упаковки. Затем эта же команда формирует
   ZIP, SHA-512 и `latest-mac.yml` из подписанного приложения в `release/production`.
2. `npm run package:update:mac` позволяет отдельно повторить подготовку
   ZIP и метаданных из уже подписанного приложения.
3. Опубликовать ZIP и `latest-mac.yml` вместе с DMG в одном стабильном GitHub
   Release с тегом `v<package.json version>` и заполненным описанием изменений.
   Публикация выполняется отдельно по поручению пользователя.

Версии должны возрастать. Не заменять файлы уже опубликованного выпуска.
Скачивается полный ZIP: дифференциальные обновления отключены, поскольку
текущая упаковка не создаёт blockmap. Для предварительной версии скрипт создаёт
`<channel>-mac.yml` (например, `rc-mac.yml`), а не стабильный `latest-mac.yml`.
Предварительные GitHub Releases не участвуют в стабильном канале. При проблеме
выпустить исправление с более высокой версией; автоматический downgrade запрещён.

Нельзя публиковать credentials, профили или тестовые данные. Используется
существующая упаковка через Electron Packager, без смены bundle ID или каталога
userData. Первый переход с ad-hoc сборки требует ручной установки подписанной
сборки. Полная проверка установки между двумя версиями возможна только с двумя
Developer ID сборками, подписанными одной командой Apple; тесты с имитацией
updater не доказывают работу системного установщика macOS.

Источники: https://www.electron.build/v26/docs/features/auto-update/ и
https://www.electronjs.org/docs/latest/tutorial/code-signing.
