# T13, срез 6 — узнавание вхождения серии в разных видах

Реализовано 29 октября 2026 года отдельным PR после слияния T12 (#34) и T13 (#35).
Основные ключи событий **не менялись**: вхождению добавлены алиасы, по которым
его узнают, когда оно меняет вид. Контракт серий на сервере не подтверждён, как и
раньше (см. [T13](t13-series-scope.md)).

## Зачем

Одно вхождение серии приходит в разных видах: виртуальное (`series:{id}:{мс}`)
и после материализации событие со своим `id` (`event:{id}`). Ключ при этом
меняется, поэтому:

- напоминание о том же вхождении приходило бы повторно;
- аналитика считала бы его дважды (ограничение T12);
- календарь мог бы показать оба вида.

## Почему не единый ключ

Первоначально планировался ключ `series:{id}:{локальная дата}` для всех вхождений.
При проверке выяснилось, что он ухудшает стабильность `event:{id}`: тест «a
materialized instance keeps its own stable ID when its start changes» и отчёт
[T11](t11-reminders.md) («перенос после доставки не повторяет уведомление»)
держатся на том, что ключ материализованного события не зависит от времени.
С ключом по дате перенос на другой день стал бы давать повторное напоминание.
Поэтому основные ключи оставлены, а связь между видами выражена алиасами.

## Алиасы

Поле `CalendarEvent.aliases` заполняется в `normalize` (`calendar.ts`) только при
наличии `original_event_id`:

| Вид                             | Основной ключ (не меняется) | Алиасы                                             |
| ------------------------------- | --------------------------- | -------------------------------------------------- |
| виртуальное (без `id`)          | `series:{id}:{мс}`          | `series:{id}:{локальная дата}`                     |
| материализованное (с `id`)      | `event:{id}`                | `series:{id}:{локальная дата}`, `series:{id}:{мс}` |
| шаблон серии с собственным `id` | `event:{id}`                | нет                                                |
| обычное событие                 | `event:{id}`                | нет                                                |

Локальная дата считается в Asia/Almaty. Второй алиас материализованного события
совпадает со старым ключом виртуального вхождения, поэтому доставки, записанные до
этой версии, тоже узнаются. Шаблон серии алиасов не получает: связь его первого
вхождения с виртуальным видом неизвестна.

## Правило «то же вхождение»

`isSameOccurrence` (`src/shared/occurrence-key.ts`): основной ключ совпал или
пересеклись идентичности (ключ плюс алиасы). Два разных события со своими `id`
не сливаются, даже если у них одна серия и один день. При слиянии остаётся
представление со своим `id`: оно текущее и его можно менять. `OccurrenceSet`
собирает события по этому правилу с индексом по идентичностям (линейно), сохраняет
порядок первого появления и прежнее правило «тот же ключ: побеждает последний».

## Где используется

- **Календарь** (`calendar.events()`) показывает одно вхождение вместо двух.
- **Расписание и окно серий** (`collectEvents`): представления из разных недельных
  чтений тоже сводятся. `series-backend.ts` читает окно через общий `collectEvents`
  вместо собственного цикла; в окне одно представление на вхождение, с `eventId` и
  актуальным временем, отсортированное по времени.
- **Аналитика** (`analyzeMeetings`): представления схлопываются до прежней проверки
  идентичности, число схлопнутых входит в `duplicates`. Ограничение T12 про дубль
  виртуального и материализованного вхождения снято.
- **Напоминания** (`reminders.ts`, `reminder-store.ts`):
  - событие считается доставленным, если в `sent` есть хеш его ключа или любого
    алиаса;
  - при доставке виртуальное вхождение записывает хеш ключа и хеш алиаса даты,
    материализованное только свой `event:{id}`: два разных события одной серии в
    один день не гасят друг друга;
  - совпадение по алиасу дополнительно записывает основной хеш;
  - схема `reminders.json` не менялась, прежние записи валидны, очистка через
    30 дней прежняя; формат каждого хеша проверяется до записи.

## Совместимость

Основные ключи, схема `reminders.json`, интерфейс и вывод для ассистента не
изменились; новое поле `aliases` необязательное и интерфейсом не используется.
Доставка, записанная до обновления под ключом виртуального вхождения, узнаётся
материализованным событием, если оно не переносилось (по алиасу `series:{id}:{мс}`).

- Unit: 30 новых тестов (модуль алиасов 9, календарь 5, напоминания 7, аналитика 4,
  расписание 2, окно серий 3). Весь набор: 296 тестов.
- Электрон: полный набор 20 сценариев, два последних полных прогона без отказов.
- Проверка чувствительности (код менялся, тест должен упасть), 29 вариантов:
  срез «алиасы и слияние» 10, «напоминания» 9, «аналитика и расписание» 6, «окно
  серий» 4. В том числе: нет старого ключа в алиасах, дата по UTC, виртуальное
  вытесняет материализованное, слияние разных `id`, потеря позиции, неочищаемый
  индекс, материализованное записывает алиасы, виртуальное не записывает алиас даты,
  `seen` не считается доставкой, нет проверки формата хеша, аналитика без схлопывания.
  Несколько вариантов сначала выживали, для них добавлены проверки.
- `npm run typecheck`, `npm test`, `npm run build:desktop`, `npm run test:desktop`,
  форматирование и `git diff --check`.

## Ограничения

- Неизвестно, отдаёт ли API `original_event_id` у материализованных вхождений
  (допущения A2/A4). Если нет, у них не будет алиасов, а дубли останутся. Без
  тестовой среды не проверить; в проверке контракта это один из пунктов.
- Исходная дата вхождения неизвестна после переноса на другой день: перенесённое
  и ранее доставленное как виртуальное вхождение даст новое напоминание.
- Доставка, записанная до этой версии и перенесённая в пределах дня уже после
  материализации, не узнаётся: в старых записях есть только хеш с минутами начала.
  Возможен один повтор при переходе на новую версию.
- Два разных события одной серии в один день, если до этого было доставлено
  виртуальное вхождение, оба узнаются по алиасу даты и будут погашены (очень
  редкий случай).
- Шаблон серии с собственным `id` алиасов не получает.
- Откат на прежнюю версию приложения может повторить уведомления: новые хеши ей
  неизвестны.
- Пока записи серий закрыты гейтом, материализованных вхождений нет и эффект
  проявится после включения записи или если сервер материализует вхождения сам.
- Полный набор Electron нестабилен независимо от этой задачи (см. [T12](t12-analytics.md)).
  Сценарий перетаскивания границы события (`calendar-short-event`, `scenario=00`)
  иногда не применяет второе растягивание. В прогонах этой ветки отказ случился один
  раз из двух первых полных наборов и ещё в нескольких запусках двух календарных
  файлов подряд. Проверено сравнением с чистым `origin/main`: при чередующихся
  запусках этой пары файлов `main` дал 1 отказ из 14, ветка 0 из 14; отдельные файлы
  на `main` 1 из 12 и 0 из 12. Регрессии от алиасов не выявлено, причина нестабильности
  не установлена.
