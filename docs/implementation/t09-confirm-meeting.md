# T09 — Подтверждение и создание разовой встречи

Карточка позволяет изменить название и адженду, затем явно создать встречу.
Редактирование увеличивает версию и сохраняет ссылку конференции. Main принимает
только ID и версию зарегистрированного черновика; подмена параметров, старая
версия и чужой аккаунт отклоняются. Модели доступна только подготовка черновика.

Перед записью повторно проверяются доступность всего состава и похожее событие
в личном календаре. Затем выполняется один POST с `force=false`, без обхода
конфликтов, повторяемости, публичности и дополнительных получателей уведомлений.
Ответ 401 не запускает refresh с повтором POST. Смена сессии до отправки отменяет
запись. Серверное создание использует контракт публичного клиента Small,
описанный в первом срезе; разрешённый тестовый backend ещё не проверен.

## Неопределённый исход

Перед POST в `userData/meeting-operations` записывается эксклюзивное намерение
с fsync файла и каталога. На диске только хеши параметров, состояние и ID события;
тексты, участники и учётные данные не сохраняются. Черновики остаются в памяти.
Ключ связывает аккаунт, состав и интервал: новая автоматическая ссылка или новый
ID черновика не позволяют повторить неизвестную операцию после перезапуска.
Повреждённый журнал также блокирует запись; автоматического удаления записей нет.

Успех показывается после чтения полученного ID и сравнения названия, описания,
места, времени, полного состава, отсутствия повторения и публичности. Несовпадение,
таймаут или ошибка оставляют неизвестный результат. Кнопка проверки только читает.
Если ID не получен, совпадение в списке не доказывает авторство операции, поэтому
не объявляется успехом и не разрешает повторный POST. Проверять нужно в календаре;
автоматического снятия блокировки в этом срезе нет.

## Новая встреча после удаления прежней

Три соседних интервала образуют три независимых ключа: подготовка черновиков
не резервирует время, каждый POST требует подтверждения своей карточки.
Блокировка другого черновика на тот же интервал означает запись о прежней
отправке в локальном журнале, а не резервирование новым черновиком.

Для нового черновика на освободившееся время main проверяет ID ранее успешно
созданного и сверенного события. Только явный ответ Small `status: cancelled`
для того же ID разрешает перейти к следующему ключу операции. Ключ вычисляется
из прежнего ключа и ID удалённого события: параллельные новые карточки используют
одну эксклюзивную запись. Прежние квитанции сохраняются, а уже открытая карточка
остаётся привязана к своей операции и не отправляет удалённую встречу повторно.

Перед новым POST повторно проверяются доступность и дубли. Само чтение черновика
не создаёт встречу. Неизвестный исход, отсутствие ID, простой 404, потеря доступа
или ошибка чтения не разрешают обход блокировки.

Проверки: unit-сценарии трёх соседних интервалов, перезапуска, повторного
использования удалённого события, параллельных новых карточек и сохранения
блокировки неизвестного исхода. Electron на синтетическом API проверяет три
карточки из одного запроса, три подтверждения, три события в сетке и создание
новой встречи на месте удалённой.

Это локальная защита в одном каталоге приложения, а не серверная гарантия
exactly-once между устройствами. Серверный idempotency key не установлен.
Изменение интервала или состава образует другой ключ. Проверка перед POST не
атомарна с серверной записью. Помещения, редактирование времени/состава в карточке,
изменение существующих событий и серии остаются за рамками среза.

## Проверки

`npm test`: 92 теста; `npm run test:desktop`: 8 сценариев.
`typecheck`, `build`, `build:desktop`, `format:check` проходят.
Упакованная сборка отдельно не проверялась.

Синтетический Electron-сценарий проверяет путь provider → SDK → main → карточка →
подтверждение → POST → GET. Включены редактирование с сохранением URL, отказ старой
версии, один POST при повторном чтении и ответ 503 после применения записи без
повторной отправки. Host resolver блокирует настоящий Small в тесте.

Модульные тесты покрывают параллельные подтверждения, эксклюзивный журнал двух
экземпляров, перезапуск, повреждённое намерение, конфликт, отказ журнала,
аккаунт, 401 без повтора, запрет force и сравнение полного ответа события.
Инверсия проверки версии ломает все четыре теста контроллера; код восстановлен.

При проверке найден и исправлен импорт Zod в sandbox preload: IPC-константы и
типы отделены от исполняемых схем. Сквозной тест проверяет работоспособность моста.
Реальные встречи и приглашения при разработке не создавались. Реальные API, GLM,
доставка приглашений, нормализация серверного описания и работоспособность комнат
конференций ещё требуют разрешённого тестового контура.
