## Условия безопасности

Проба пишет в календарь, поэтому запускается только так:

1. Есть явное разрешение владельца среды на тестовые записи и **тестовый календарь**
   (его `id` известен). Реальные календари сотрудников не используются.
2. Только синтетические события с названием `T13-PROBE-…`, без реальных участников
   (`participant_ids: []`) и без приглашений. Если сервер требует участника, проба
   останавливается и фиксирует это: участников она не придумывает.
3. Скрипт создаёт события сам и меняет/удаляет только их (и их вхождения). Любой
   запрос к чужому `id` отклоняется до отправки. Лимит — 30 записей за запуск.
4. Куки сессии передаются только переменной окружения `SMALL_PROBE_COOKIE`; они не
   пишутся в вывод и не сохраняются. В результат попадают псевдонимы вместо `id`,
   хеш хоста и коды ответов, без названий, описаний и людей.
5. После прогона скрипт удаляет всё созданное и сообщает итог очистки. Если очистка
   не удалась, вручную удалить события с префиксом `T13-PROBE-` в тестовом календаре.

Запуск без `--execute` ничего не читает и не отправляет: печатает план.

```bash
node --import tsx scripts/series-probe.ts
node --import tsx scripts/series-probe.ts --execute \
  --base-url https://<тестовый-хост> --allow-host <тестовый-хост> \
  --calendar-id <id> --confirm <тестовый-хост>:<id> --out series-probe-result.json
```

`SMALL_PROBE_COOKIE` — значение заголовка `Cookie` авторизованной тестовой сессии.
Для проверки прав (эксперимент E8) дополнительно `SMALL_PROBE_COOKIE_OTHER` —
сессия другого тестового аккаунта, не организатора.

## Допущения, которые нужно подтвердить

Клиентский код T13 строится на этих допущениях; до проверки они остаются
предположениями.

| №   | Допущение                                                                                                                                                                                    | Эксперимент |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| A1  | `GET /calendar/events/generated` отдаёт виртуальное вхождение и ничего не создаёт                                                                                                            | E2          |
| A2  | `POST /calendar/events/from-template` по `original_event_id` и локальной дате возвращает событие с `id`; повторный вызов с теми же параметрами идемпотентен (тот же `id`) либо создаёт дубль | E3          |
| A3  | `PUT … recurring_edit_type: single` на материализованном вхождении меняет только его                                                                                                         | E4          |
| A4  | После переноса вхождения исходная дата больше не показывает второе виртуальное вхождение, а перенесённое адресуется стабильно                                                                | E4          |
| A5  | `all-next` меняет вхождения с выбранной даты вперёд и не затрагивает прошлые                                                                                                                 | E5          |
| A6  | `UNTIL` включает вхождение в день `UNTIL`                                                                                                                                                    | E1          |
| A7  | Отмена и удаление вхождения не затрагивают остальные; различие cancel/DELETE и вид исключения                                                                                                | E6          |
| A8  | Локальная дата вхождения — дата `starts_at` в Asia/Almaty; смещения стабильны                                                                                                                | E1, E4      |
| A9  | Не организатор получает отказ на PUT/cancel/DELETE                                                                                                                                           | E8          |
| A10 | В ответах нет ETag/Last-Modified, защита от конкурентной правки не предусмотрена                                                                                                             | E7          |

## Эксперименты

Каждый эксперимент записывает: список запросов (метод, шаблон пути с псевдонимами,
код ответа) и наблюдения. Тела с личными данными не сохраняются.

- **E1. Создание серии и чтение.** Серия WEEKLY, один день недели, `UNTIL` = дата
  третьего вхождения; чтение периода `GET /calendars/my/events`. Фиксируем: число
  вхождений и есть ли вхождение в день `UNTIL` (A6); у вхождений `id` или
  `original_event_id`, поле `is_recurring`, смещения `starts_at` (A8).
- **E2. Виртуальное вхождение.** `GET /calendar/events/generated` для второго
  вхождения; затем повторное чтение периода. Фиксируем: ответ не создал событие (A1).
- **E3. Материализация.** `POST /calendar/events/from-template` для второго
  вхождения дважды подряд. Фиксируем: оба кода ответа, одинаков ли `id`, число
  вхождений после (A2). Это же определяет, чем опасен повтор после неизвестного
  исхода; приложение в любом случае не повторяет запись вслепую.
- **E4. `single` и перенос.** `PUT /calendar/events/{id}?force=false` на
  материализованном вхождении с `recurring_edit_type: single`, сдвиг на час и на
  другой день. Фиксируем: меняются ли остальные вхождения (A3), остаётся ли
  виртуальное вхождение на исходной дате, ключ перенесённого (A4, A8).
- **E5. `all-next`.** PUT с `recurring_edit_type: all-next` на третьем вхождении
  (сдвиг на час). Фиксируем: что изменилось у первого и второго вхождений (A5),
  новый ли `original_event_id` у последующих. Значения `all` и `future` не
  отправляются: семантика не подтверждена, проба только читает, что отвечает сервер
  на `all-next`.
- **E6. Отмена и удаление.** `POST /calendar/events/{id}/cancel` для одного
  материализованного вхождения и `DELETE` для другого. Фиксируем: что исчезло из
  чтения периода, остались ли остальные вхождения, как выглядит исключение (A7).
  Форма тела cancel (`reason`) взята из клиентского кода и не подтверждена.
- **E7. Заголовки.** Чтение `GET /calendar/events/{id}`: есть ли `ETag`,
  `Last-Modified` (A10). Только чтение.
- **E8. Права (необязательно).** Те же PUT/cancel/DELETE от второй сессии на
  событие первой: коды ответов (A9). Выполняется только при `SMALL_PROBE_COOKIE_OTHER`.

## Критерии включения операций (переход гейта в `verified`)

Гейт включается отдельно для каждой операции и только после записанных результатов:

- переименование и перенос «только это вхождение»: A3, A4, A8 подтверждены, а для
  виртуального вхождения (материализация входит в запись) ещё и A2;
- область «это и последующие»: дополнительно A5 и A6;
- удаление вхождения: A7 и A9 (и A2 для виртуального);
- удаление «последующих» и всей серии в первую версию не входит.

Опровергнутое допущение меняет адаптер или оставляет операцию закрытой; код
не подстраивается под наблюдение без обновления этого протокола.

## Что проба не доказывает

Один прогон на тестовой среде не доказывает поведение на других инстансах и
не заменяет серверную документацию. Конкурентные правки, rate limits и повторы
после реального таймаута она не воспроизводит.
