# Team Small: проверка интерфейса и клиентского API

Дата исследования: 28 октября 2026 года. Это восстановленный клиентский
контракт, **не серверная OpenAPI-схема** и не отчёт о проверке записей.

## Источники и границы проверки

- [Текущий календарь](https://team.small.kz/calendar), HTML получен без авторизации.
- Обслуживаемый им [JavaScript bundle](https://team.small.kz/assets/index-Dwj9jIUp.js),
  SHA256 `048bc4eb0b16ac72976f2f51760a54e92e1fa4456ae318f0d5952e3b58f5f355`.
  Имена функций ниже — поисковые якоря именно этой сборки.
- Изученные ранее материалы `Work tasks`: справочник API, Python-клиент
  и история интеграции; исторические результаты не заменяют текущую проверку.
- [Frontend](https://gitlab16.skiftrade.kz/staff/team-small-kz-frontend)
  и [backend](https://gitlab16.skiftrade.kz/staff/team-small-kz-backend)
  в GitLab перенаправили запросы на страницу входа. Их исходники и серверные
  ограничения в этом исследовании недоступны.

Локальная папка `calendar` также просмотрена, но её происхождение и соответствие
текущему Team Small не установлены; выводы ниже основаны на обслуживаемом bundle.
Никакие пользовательские токены не читались, встречи не создавались.
Bundle сохранён только во временной папке, в репозиторий не включён.

## Представления и настройки

В `Dqa` и `SJr` перечислены три представления:

| Название | Значение |
| --- | --- |
| День | `timeGridDay` |
| Неделя | `timeGridWeek` |
| Месяц | `dayGridMonth` |

В `OB` исходное представление — день. Store `calendar-storage` сохраняет
`calendarView` и `selectedCalendars`; есть переключатель `myCalendar`.
`Hqa` показывает выбор доступных публичных календарей/переговорных.
Это подтверждённый минимум для требования «всё, что есть в Team Small».
Наличие внутренних FullCalendar view в библиотеке не означает их доступность
в пользовательском интерфейсе. Полную визуальную эквивалентность ещё нужно
сверить с авторизованным интерфейсом, включая фильтры и доступные действия.

## Профиль, права и каталог

| Назначение | Найденный метод | Ограничение вывода |
| --- | --- | --- |
| Вход / refresh / выход | `POST /gate/auth/login`, `/refresh`, `/logout` (`htt`, клиент `m0e`) | Refresh использует cookies; серверное поведение отзыва нужно проверить. |
| Текущий пользователь | `GET /gate/team/api/user/info` (`bF.getUserInfo`) | Схему ответа и стабильный идентификатор проверить авторизованным чтением. |
| Права Team | `GET /gate/team/api/user/permissions` (`hzn`) | Это отдельный endpoint от прав access-management. |
| Поиск сотрудников | `GET /gate/employee/api/search/persons` (`qXn`, клиент `g2`) | Параметры `q`, `per_page`, `page`; ответ `data.items` и `data.pagination.current_page/last_page`. |
| Каталог персон | `/api/persons` присутствует в таблице маршрутов | Не доказаны параметры и пригодность для полного состава команды. |
| Дерево оргструктуры | `GET https://gate-business.skiftrade.kz/team-persona/org-units/{id}/card-focus` (`S0t`, `s8r`) | Для root передаётся `depth`, для других узлов `parent`. |
| Сотрудники подразделения | `GET https://gate-business.skiftrade.kz/team-persona/org-units/{id}/card-employees` (`z8s`) | Для не-root передаётся `parent`; полнота, вложенные команды и схема ответа не установлены. |

Поиск использует `person_guid`. Нельзя автоматически считать его календарным
`participant_id`: нужен подтверждённый mapping по реальным ответам/исходникам.
Наличие employee API не закрывает вопрос полного состава команды, активных
сотрудников, пагинации дерева и прав на чтение другого сервиса.

## Календарные методы

Клиент `Zi` имеет base URL `/gate/team/api`; объект методов — `Tf`.

| Операция | Метод и путь относительно base URL |
| --- | --- |
| Мои события | `GET /calendars/my/events` |
| Доступные публичные календари | `GET /calendars/public` |
| События календаря | `GET /calendars/{id}/events` |
| Карточка | `GET /calendar/events/{id}` |
| Создать / изменить | `POST /calendar/events`, `PUT /calendar/events/{id}`, query `force` |
| Отменить / удалить | `POST /calendar/events/{id}/cancel`, `DELETE /calendar/events/{id}` |
| Занятость | `POST /calendar/events/busy-intervals` |
| Слоты | `POST /calendar/events/find-slots` |
| Ответить на приглашение | `PATCH /calendar/events/{id}/participant-status`, `accepted` / `declined` |
| Проверить доступность | `POST /calendar/events/{id}/check-availability` |
| Получить виртуальное вхождение | `GET /calendar/events/generated?original_event_id=…&date=…` |
| Материализовать вхождение | `POST /calendar/events/from-template` |

В `x8a` запрос занятости включает `participant_ids`, `date`, `timezone`
и необязательные `calendar_ids`. В `S8a` поиск использует `participant_ids`,
`duration_minutes`, `start_date`, `timezone`, `include_weekends: false`
и необязательные `calendar_ids`; читает `data.available_slots`.
Горизонт поиска, лимиты группы, серверная пагинация и rate limits не установлены.

## Повторяемость: факты из кода

- Создание передаёт `recurrence_type: custom`, `recurrence_rule` с
  `FREQ: WEEKLY`, `BYDAY`, `UNTIL`. Это не доказательство поддержки всех RRULE.
- Диалог редактирования `rZr` предлагает `single` или `all-next`.
  Enum также содержит `all` и `future`, но одно наличие enum не определяет
  серверную семантику этих значений.
- Если у события есть `original_event_id`, перед редактированием код вызывает
  `from-template` с `original_event_id` и локальной датой вхождения.
  Это запись, её нельзя использовать для просмотра или аналитики.
- Диалог удаления различает текущее вхождение и серию; код использует cancel
  или delete. Влияние на прошлые/будущие вхождения требует серверной проверки.

До включения записей серий нужно подтвердить: inclusivity `UNTIL`, область
`all-next`, отмены/исключения, идентичность перенесённого вхождения,
таймзоны и поведение повторного `from-template` после неизвестного результата.

## Следующая техническая валидация

Проверить авторизованным чтением профиль, права, mapping людей и структуру
ответов; получить доступ к исходникам backend или схеме API. Серийные записи
проверять на синтетических событиях в тестовом окружении. Не переносить
персональные данные из ответов в репозиторий. Пределы API фиксировать по
серверной документации или результатам согласованных проверок, не угадывать.
