# ADR-002: стек десктопного приложения

## Статус и дата

**Принято: Electron + React + Dockview Community**, 28 октября 2026 года,
по явному решению пользователя. Выбор стека не подтверждает будущие интеграции
Keychain и уведомлений; они проверяются отдельными срезами.
Заменяет десктопную часть [ADR-001](001-desktop-and-agent-harness.md).

## Решаемый вопрос

Как собрать macOS-приложение с настраиваемыми виджетами календаря/ассистента,
нативными уведомлениями, Keychain и фоновым режимом при закрытом окне?
Выбор AI-харнеса рассматривается независимо в [ADR-003](003-agent-harness.md).
Здесь определяется только возможность запуска доверенного TypeScript/Node.js-кода.

Первая целевая среда проверена локально: macOS **15.1**, build **24B2083**,
Apple Silicon **arm64**. Поддержку других версий и архитектур пока не обещаем.

## Решение

| Часть | Выбор | Причина |
| --- | --- | --- |
| Оболочка | Electron | Встроенные Chromium и Node.js; один распространяемый пакет без отдельной установки Node у коллег. |
| UI | Локально собранный React + TypeScript | Календарь и ассистент — части управляемого приложением рабочего пространства. |
| Компоновка | Dockview Community | Перетаскивание панелей между областями, resize границами и сериализация layout без собственной docking-системы. |
| Календарь | Переиспользовать доступные исходники frontend после проверки доступа и лицензии | Сохранить поведение Team Small; не копировать минифицированный bundle как исходник. При недоступности исходников нужен отдельный выбор календарного компонента. |
| Keychain | Отдельный адаптер прямого доступа; кандидат `@napi-rs/keyring` | Секреты в Keychain по аккаунту/профилю; native binding требует проверки в подписанной arm64-сборке. |
| Уведомления | Electron Notification из main | Центр уведомлений macOS, содержание встречи и действие «Подключиться». |
| Локальные настройки | Layout, представление и выбранные календари | Предложение сохранять компоновку между запусками; формат/версионирование уточнить в реализации. |

[Electron](https://github.com/electron/electron/blob/main/README.md#platform-support)
публикует Apple Silicon binaries и поддерживает macOS Ventura и новее.
Это основание для выбора кандидата, не подтверждение запуска нашего приложения.
[Dockview](https://dockview.dev/docs/overview/introduction/) поддерживает docking,
resize и сериализацию; [MIT Community](https://dockview.dev/docs/overview/licence/)
достаточно для этих возможностей, Enterprise не требуется.

## Границы процессов

- Renderer — локальный UI: без Node.js, секретов и raw IPC. Включены sandbox,
  `contextIsolation`; bridge предоставляет конкретные операции с валидацией.
- Main — жизненный цикл, Keychain, API календаря, напоминания и открытие URL.
- Utility process — доверенный runtime ассистента, общающийся с main через
  ограниченные сообщения. Изолирует сбои; сам по себе не является security sandbox.
- Не предоставлять удалённому веб-контенту Small привилегированный bridge.
  Выбор библиотеки харнеса не меняет эти границы и не даёт модели доступ к ОС.

Основание: [security](https://www.electronjs.org/docs/latest/tutorial/security)
и [utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process).

## Особенности macOS

[Notification](https://www.electronjs.org/docs/latest/api/notification) позволяет
показывать title/subtitle/body и macOS actions. Нужны название встречи,
начало/окончание, организатор и действие открытия сохранённого URL.
Не полагаться на кликабельность произвольной строки URL в body. Ссылку не
проверять сетевым запросом; перед открытием проверять формат и допустимую схему.
Вид и показ уведомлений зависят от macOS, разрешений и Focus.
Актуальная документация требует подписи приложения для доставки уведомлений.

Закрытие окна сохраняет main и планировщик работающими; полный выход —
отдельная команда. Уведомления не зависят от работоспособности модели.

[Keyring binding](https://github.com/Brooooooklyn/keyring-node) — кандидат,
а не установленная зависимость. Сессии и LLM-ключи хранятся раздельно.
[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)
шифрует данные для хранения на диске с OS-backed ключом; это не прямое
хранение самих сессионных секретов в Keychain и не подмена требования AUTH-2.

## Альтернативы

| Вариант | Сильная сторона | Компромисс для этого приложения |
| --- | --- | --- |
| Electron | Готовый Node runtime и web UI в одном пакете | Размер Chromium/Node и память; нужны обновления и корректная подпись. |
| Tauri + Node sidecar | Системный webview, возможен меньший пакет | Для выбранного Node runtime нужны sidecar, его упаковка, жизненный цикл и Rust-граница. |
| Pake | Быстрая упаковка существующего сайта | Своя компоновка, runtime ассистента и Keychain всё равно требуют существенной разработки. |
| SwiftUI + TS-сервис | Нативный UI и прямые API macOS | Два стека и мост к TypeScript; больше интеграционной работы на старте. |

Источники: [Tauri sidecar](https://v2.tauri.app/develop/sidecar/),
[Pake](https://github.com/tw93/Pake), [SwiftUI](https://developer.apple.com/swiftui/).
Оценка трудоёмкости — инженерный вывод из состава компонентов, не измерение.
Если приоритетом станет минимальная память/размер или полностью нативный UI,
выбор нужно пересмотреть с измерениями, включая Tauri и SwiftUI.

## Последствия и проверки реализации

Преимущество — единая среда TypeScript для приложения и runtime ассистента.
Цена — более крупная оболочка и сопровождение Electron/native binding.
Фреймворк не гарантирует ни минимальный расход памяти, ни работу Keychain
и уведомлений в конкретной упакованной сборке.

При реализации: упаковать arm64-прототип для macOS 15.1; проверить запуск,
Keychain на синтетическом секрете с очисткой, отказ доступа, подписанное
уведомление с открытием тестового URL, resize/перемещение панелей и закрытие
окна без остановки напоминаний. Точные версии, build tooling и команды
фиксировать в манифесте. T02 проверяет окно и локальную упаковку; Keychain,
уведомления и Dockview проверяются в соответствующих следующих срезах.
