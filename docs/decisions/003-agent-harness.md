# ADR-003: AI-харнес для календарного ассистента

## Статус и дата

**Принято: выбор Vercel AI SDK (Core + UI)**, 28 октября 2026 года,
по явному решению пользователя. Совместимость Small endpoint и детали
реализации ещё требуют проверки; выбор библиотеки их не подтверждает. Заменяет часть о харнесе из [ADR-001](001-desktop-and-agent-harness.md).
Десктопная оболочка, UI-компоновка и API macOS определяются в
[ADR-002](002-desktop-stack.md) и не являются аргументами выбора библиотеки агента.

## Решаемый вопрос

На чём построить TypeScript-ассистента, который находит время, готовит встречи,
показывает подтверждение и получает аналитику через узкие инструменты?
Подключения: корпоративный Small vLLM либо персональный OpenAI-совместимый
endpoint; GLM / DeepSeek Flash — кандидаты до получения точных model ID.

Нужны: streaming, валидируемые инструменты, управляемый цикл, отмена запроса,
UI состояний инструментов, сохранение черновика и безопасная запись после сбоя.
Не заявлены автономные многочасовые процессы, совместное управление одним
агентом или исполнение моделью произвольного кода.

## Решение и его граница

Использовать **Vercel AI SDK (Core + UI)** для прикладного TypeScript-харнеса.
Основные блоки: `ToolLoopAgent`, прямой OpenAI-compatible provider и UI-состояния
инструментов. Общую механику SDK переиспользуем, бизнес-правила Small,
подтверждённые черновики и журнал операций остаются в коде приложения.

Основание принятия — выбор пользователя после рассмотрения альтернатив.
Это не результат бенчмарка и не утверждение превосходства по всем критериям.
eve, Pi-core и другие варианты остаются в ADR как рассмотренные альтернативы;
их внедрение и сравнительные прототипы не входят в текущий план.

Core — часть Vercel AI SDK для моделей и инструментов, UI — часть для сообщений
и состояний чата. Для прикладного харнеса используем `ToolLoopAgent`
с прямым OpenAI-compatible provider. Это строительные блоки, не готовый
durable-харнес: хранение истории, черновиков и журнала операций организует
приложение. Для этого варианта Vercel hosting/Gateway не требуются;
инфраструктурные требования eve оцениваются отдельно ниже.

Отдельная экспериментальная абстракция SDK `HarnessAgent` для внешних runtimes
не равна eve или Core-loop. Запуск coding-agent здесь не предлагается.
[Различие Core и Harnesses](https://ai-sdk.dev/docs/ai-sdk-harnesses/overview).

## Рассмотренные готовые примеры

Сходство оцениваем по устройству агента, а не по работе с календарём:
сессии, история, цикл инструментов, взаимодействие с пользователем,
подтверждение действий и продолжение диалога.

| Пример | Что уже есть | Как использовать |
| --- | --- | --- |
| [eve Chat Template](https://github.com/vercel/eve/tree/main/apps/templates/eve-chat-template) | Web-чат, история, инструменты, HITL-компоненты, сохранение событий и курсора сессии | Рассмотренная альтернатива. Для выбранного SDK-loop не подключается; перенос runtime/UI из web не входит в план. |
| [eve Contentful Assistant](https://eve.dev/templates/eve-contentful-agent-template) | Поиск, подготовка изменений, карточка подтверждения перед публикацией через Slack | Образец многошагового действия с участием человека; публикация в Contentful не является календарной операцией, правила подтверждения переносим отдельно. |
| [Vercel Chatbot](https://github.com/vercel/chatbot) | Чат на базовом Vercel AI SDK, streaming, tools и сохранение истории | Образец UI и интеграции выбранного SDK. Веб-хранилище и облачную авторизацию не переносим автоматически. |

В [исходниках шаблона](https://github.com/vercel/eve/blob/main/apps/templates/eve-chat-template/apps/web/app/_components/agent-chat.tsx)
используются `useEveAgent`, состояния сессии и stream events.
[Описание архитектуры](https://github.com/vercel/eve/blob/main/apps/templates/eve-chat-template/docs/how-the-chatbot-works.md)
разделяет agent, web UI, persistence и auth. Это готовый пример, а не уже
проверенная desktop-интеграция.

Ограничения по [README шаблона](https://github.com/vercel/eve/blob/main/apps/templates/eve-chat-template/README.md):
в starter-режиме история и курсоры хранятся в браузере, общий пароль даёт
одну агентную идентичность; такой режим не подходит нашим нескольким аккаунтам.
Production-режим предлагает Neon, Upstash и отдельное хранилище памяти.
Эти зависимости нельзя автоматически объявить ни обязательными для любого eve,
ни готовыми к замене локальным хранилищем без проверки. Node.js runtime,
локальное хранение, выбор модели, Keychain и восстановление требуют spike.

В [документации eve](https://github.com/vercel/eve) есть sessions, tools и skills;
[approval policy](https://github.com/vercel/eve/blob/main/docs/patterns/multi-tenant-approvals.md)
позволяет учитывать активную сессию, имя инструмента и аргументы.
Это уменьшает предполагаемый объём общей обвязки; изоляцию аккаунтов, версию
карточки и отсутствие дублей календаря всё равно обеспечивает наш сервис.
Совместимость eve с корпоративным Small vLLM/GLM/DeepSeek ещё не проверялась.

## Аргументы выбранного решения

### 1. Один формат от tool call до карточки в чате

Для календаря UI должен показывать «ищу слоты», результат, черновик, ожидание
подтверждения и ошибку как разные состояния. [Vercel AI SDK UI](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-tool-usage)
даёт типизированные части сообщений для инструментов и approval response;
это позволяет связать чат и календарные карточки с событиями Core без создания
ещё одного общего формата сообщений. Это преимущество интеграции продукта,
а не уникальная способность LLM вызывать инструменты.

[Transport API](https://ai-sdk.dev/docs/ai-sdk-ui/transport) допускает свой transport.
Для desktop IPC адаптер всё равно нужно написать; стандартный `/api/chat`
не появится сам. Преимущество над Pi-core — меньше собственного общего UI-протокола,
но Pi также можно адаптировать к этому UI. Одно наличие React не доказывает
превосходство Vercel AI SDK.

### 2. Контролируемый loop без обязательного workflow-движка

[ToolLoopAgent](https://ai-sdk.dev/docs/agents/building-agents) и
[loop control](https://ai-sdk.dev/docs/agents/loop-control) дают цикл с
`stopWhen` и `prepareStep`: можно менять доступные инструменты по стадии,
останавливать лишние шаги и отдельно выдавать ошибки. Для интерактивного
«найти → предложить → подготовить» это позволяет начать с малого.
Выигрыш относительно LangGraph/Mastra — возможность не вводить graph/workflow
модель для короткого диалога. Это вывод о подходящем объёме абстракций,
а не утверждение, что конкуренты обязательно требуют сложной архитектуры.

### 3. Прямое подключение к endpoint без облачного посредника

[OpenAI-compatible provider](https://ai-sdk.dev/providers/openai-compatible-providers)
поддерживает `baseURL`, `apiKey`, `modelId`, custom `fetch` и настройки
возможностей. Это соответствует двум профилям подключения и позволяет
держать ключи за пределами renderer/модельного контекста.
Этот критерий проходят и другие кандидаты; сам по себе он не выделяет Vercel AI SDK.
Реальную совместимость GLM/DeepSeek с parser Small vLLM необходимо проверять.

### 4. Стандартные состояния подтверждения и воспроизводимые проверки

[Tool approval](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling)
представлен отдельными запросом/ответом, а не фразой модели «пользователь согласен».
[Testing utilities](https://ai-sdk.dev/docs/ai-sdk-core/testing) позволяют
подменять ответы модели и воспроизводить ошибки и последовательности инструментов.
Это экономит написание общей механики по сравнению с loop с нуля.
Это не исключительное преимущество над Pi/LangGraph и не гарантия корректности
календарных записей: проверку прав, версии карточки и дубликатов пишем сами.

**Аргумент за собственный вариант — сочетание Core, UI и тестовых средств
в одном SDK** для коротких интерактивных сценариев. Рассмотрение eve показало альтернативный путь с готовым runtime,
но пользователь выбрал базовый SDK. Планируем ограниченную прикладную обвязку
и явно учитываем стоимость её сопровождения. Не доказаны меньшая задержка,
меньшая стоимость разработки или лучший tool calling, чем у Pi-core.
Такие преимущества не считаются доказанными; сравнение не является условием
начала реализации выбранного SDK.

Ниже факты по официальным источникам на дату исследования. «Приложение»
означает, что нужную гарантию обеспечивает наш код, а не отсутствие возможности.

| --- | --- | --- | --- | --- |

| Pi agent-core + pi-ai | Stateful Agent, events, последовательные/параллельные tools | `beforeToolCall` может блокировать; UI ожидания и продолжение связывает приложение | Сериализация контекста доступна; durable execution отдельно в Pi Durable | Низкоуровневые события, свой UI-адаптер |

## Компромиссы и условия выбора

| Кандидат | Сильный аргумент в его пользу | Компромисс / условие выбора |
| --- | --- | --- |
| eve | Готовые сессии, инструменты, skills и пример чата с взаимодействием с пользователем | Рассмотрен, но не выбран пользователем. Web/hosted-шаблон не является готовым desktop-пакетом. |
| Vercel AI SDK (Core + UI) | Прямой контроль над узкой обвязкой и стандартный UI-протокол | Выбран пользователем; необходимо реализовать свою ограниченную модель операции и хранение состояния. |
| Pi-core | Прямой контроль событий, context transformation и hooks без UI-ориентации; близкий конкурент для небольшого встроенного агента | Рассмотренная небольшая альтернатива; отдельный прототип сейчас не требуется. |
| Pi Durable | Persist-before-output и replay policy уже часть runtime: меньше собственной общей механики восстановления | Experimental API — риск сопровождения; длительные durable-процессы пока не заявлены. При их появлении это реальное преимущество над Core-loop. |
| LangGraph | Явные переходы, durable checkpoints и прерывания удобны для сложных согласований | Для текущего диалога граф пока не даёт доказанной пользы относительно локальной модели операции. При нескольких стадиях/участниках согласования предпочесть повторную оценку LangGraph. |
| Mastra | Agents, workflows и storage как единый framework, полезно при расширении ассистента в платформу | На старте используем меньший набор функций. Дополнительные абстракции и настройку хранилища нужно оправдать сценариями; облачный сервис не объявляется обязательным. |
| Hermes | Подходит, если нужен готовый общий ассистент, его skills и широкий инструментарий | Не соответствует предпочтению TS-runtime; Python и адаптация общего runtime усложняют desktop-пакет. Это не оценка качества Hermes. |
| Loop с нуля | Максимальный контроль и минимум внешних API-абстракций | Поддержка stream parsing, tools и UI-протокола становится нашей постоянной работой. |

Наличие durable runtime ни у одного кандидата само по себе не даёт exactly-once
для Team API. После таймаута сервер мог создать встречу до сохранения результата
локально. Нужны идемпотентность backend либо сверка операции перед повтором.
Pi Durable явно позволяет задавать replay policy — это преимущество, но не
замена поддержки идемпотентности календарём. В LangGraph нужно отдельно
учитывать повторное выполнение кода до `interrupt`.

## Что остаётся ответственностью приложения при любом выборе

- Прикладные состояния: параметры → слоты → черновик → подтверждение →
  повторная проверка → запись → сверка результата.
- Узкие схемы инструментов, авторизация и проверка доступности всех участников.
- Сохранение календарного черновика и журнала намерения до записи;
  восстановление со статусом «исход неизвестен», когда запись могла произойти.
  Сохранение общей истории/сессий можно делегировать готовому runtime,
  но его store должен быть настроен и изолирован по аккаунтам.
- Подтверждение привязано к аккаунту и версии неизменённой карточки. Изменение
  данных инвалидирует разрешение; модель не может выдать его сама.
- Арифметика аналитики выполняется кодом. Уведомления живут вне LLM-loop.
- Профили endpoint/ключа из Keychain; без автоматического fallback на внешний
  сервис. Токен не отправляется на другой origin при redirect.

Стандартный approval SDK требует продолжения с approval response и может
добавлять модельный вызов. Для фиксированной карточки встречи предлагается
после нажатия кнопки вызывать календарный сервис напрямую из доверенного
контроллера, затем показывать проверенный результат. Не требуется повторная
генерация модели для выбора уже подтверждённых аргументов. То же можно сделать
на любом из сравниваемых runtimes; это не отдельное преимущество Vercel AI SDK.

## Проверка реализации и условия пересмотра

Принятый выбор переводит работу к [плану реализации](../../tasks/plan.md).
Проверять Vercel AI SDK, не запускать сравнение харнесов заново:

1. Сначала синтетическая модель и безопасные tools: streaming, ошибки схем,
   отмена, запрос уточнения и продолжение через UI-состояния.
2. Затем прямой Small vLLM / персональный OpenAI-compatible endpoint:
   реальные model ID и корректные tool calls без автоматического fallback.
3. Подтверждение неизменённого черновика, сохранение истории и восстановление
   после сбоя с изоляцией аккаунтов; запись с неизвестным исходом не повторять.
4. Проверка transport и Node runtime в выбранной desktop-оболочке;
   секреты через OS-адаптер без передачи их модели.

Точные версии SDK, provider, UI и runtime фиксируются в манифесте/lockfile
первого среза, затем команды проверки берутся из созданного манифеста.
На момент принятия ни один кандидат не запускался на корпоративном Small
endpoint; установленных зависимостей в этом репозитории ещё нет.

Вернуться к выбору харнеса можно при подтверждённой несовместимости,
неприемлемом объёме собственной инфраструктуры или новых требованиях
к длительному durable execution. Такое изменение требует нового решения,
а не молчаливой замены библиотеки во время разработки.
